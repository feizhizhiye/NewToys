## 三、技术要点

1. 🔴 **JS 不要直接暴露 CLR 对象**。桥只暴露**固定 arity 的 `Func<string…,string>`**，参数与返回值统一 `string`；
   复杂对象（元素集 / 连接）用 JSON 串进出，由 prelude 里的 JS 还原成对象。
   理由：Jint 的 interop 参数推断（`object` / `params` / `JsValue[]`）版本间差异大，string 是最不会踩坑的边界。
2. 🔴 **`@js:` 之后不参与 `||` / `&&` / `##` 切分**（那里是 JS 逻辑运算符）。切分顺序：先剥 `@js:`（或 `<js>…</js>`），
   剩下的 head 走既有链路求值得到 `result`，再执行 code。
3. 🔴 **`java.getString(rule)` 必须回到同一个 `RuleContext` 求值**（作用域 = 当前条目节点），否则书单字段错位。
4. 🔴 **`java.ajax` 是同步语义但要真异步发**：`Task.Run(() => FetchAsync(...)).GetAwaiter().GetResult()`，
   ⛔ 直接阻塞 UI 线程上的 async（会死锁）。
5. 🔴 **判定降级**：`NeedsJs` 拆成「可跑（含 JS）」与「需 WebView」两档 —— 只在规则出现 `webview` / `startBrowserAwait` 时才拒跑。
6. 单次求值一个 `Engine` 实例（用完丢弃），避免全局变量在书源之间串味；`@js:` 片段不设语句上限，
   但必须 try/catch 包死，异常转成 `ctx.Errors` 的可读一行，⛔ 不冒到 UI。

## 五、验收标准

1. `@js:` / `<js>` 字段能求值：`class.x@text@js:result.replace("作者：","")` 正确去掉前缀。
2. `java.getString("class.a@text")` 在条目上下文内取到**该书**的值（不是整页第一个）。
3. `{{java.md5Encode(key)}}` 这类函数调用式插值不再被判「需 JS」而废弃。
4. 书源页三档变为 `可用 / 含 JS / 不完整`；审计里 111 条 B 档源的 `Capability` 变为可跑。
5. JS 抛异常 / 超时不影响同一条源其它字段；错误条能显示「哪条规则 · 什么原因」。
6. `accept.ps1` 6 项静态检查 PASS，`RuleEvaluatorTests` 原有 30 条不回归，新增 JS 用例通过。

## 六、风险

- Jint 3.1.2 **没有语句数 / 超时上限**（`Options.Constraints` 只管递归深度与正则超时）⇒ 恶意/写错的书源 JS 可能长跑。
  缓解：单次求值一个 Engine、异常包死；后续若真遇到，再评估升级 Jint 4.x。
- 桥接层是 string 边界，元素集走 JSON 快照 ⇒ 超大页面（几千节点）取 `getElements` 会有一次序列化开销。
  实测书源单次取几十到几百节点，可接受。
