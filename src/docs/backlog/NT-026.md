## 背景 / 目标（用户原话转述）

> "我建了一个小库，想把它加到更大的库里 —— 得先打开再合并；全部资产页能实现各个分类库的**加减融合**。"

即：**两个 `newtoys.db` 之间的合并 / 剪裁**。典型场景：
- 移动硬盘上单独建的小库 → 合进主力库；
- 按分类维护多个库（视频库 / 音乐库 / 书库），需要时能合、也能再删掉不要的部分。

## 🔴 用户定调的交互（2026-10-14，权威）

> "库的合并很容易理解，就是我先打开一个数据库文件，然后再打开一个数据库文件，然后点保存；库的删减就只做选择后删除吧。"

**工作副本（working set）模型** —— 与"打开一个库就切换过去"完全不同：

1. **打开库 A**（工具条「🗄 打开库文件」）→ A 的内容进当前**工作副本**；
2. **再打开库 B**（同一个按钮）→ B 的内容**并入**当前工作副本（不是切换）；
3. **💾 保存** → 把工作副本写回文件（另存 / 覆盖，需二次确认目标路径）；
4. **"减" = 勾选行后删除**（`🗑 删除选中`，走既有软删除 → 回收站 / 或物理删除按钮）；⛔ **不做**"按来源库拆出去"。

⇒ 🔴 **原「加 `assets.origin` 列 + 按来源移除」的方案作废**（用户已明确"减"只需选择后删除）。旧评估结论保留在下方备查。

## 关键设计（评估结论）

### 合并（＋）

SQLite 原生支持挂载外部库，是最省力的做法：

```sql
ATTACH DATABASE 'D:\small\newtoys.db' AS src;      -- ⛔ 只读语义：我们不写 src
```

按表逐个并入，全部放进**一个事务**：

| 表 | 去重 / 处理 |
|---|---|
| `storages` | 按 `root_path` 去重（已存在就用现有 id） |
| `assets` | **一律新建**（id 会变）→ 用临时表记 `src_id → new_id` 映射 |
| `file_locations` | `asset_id` 按映射改写；同 `(storage,relative_path)` 或同 `hash+size` 已存在 → **跳过**（不重复建） |
| `tags` / `categories` / `collections` | 按名字去重（`tags` 是 `namespace+name`），拿到本库 id |
| `asset_tags` / `asset_categories` / `collection_assets` | 两侧 id 都换成新 id 后插入，主键冲突忽略 |
| `relations` | 两端 asset id 都按映射改写 |
| `operation_logs` / `scan_jobs` / `scan_errors` | ⛔ **不合并**（属于各自库的运维历史，混进来没有意义） |

- 结果回报：`新增资产 N / 新增位置 M / 跳过重复 K / 失败 E`（写状态栏 + `scan_jobs` 记一笔）。
- ⛔ **绝不修改源库文件**（只挂载读）；⛔ 不做"移动"（复制语义更安全，源库保留）。

### 保存（💾）与工作副本

- 🔴 **未决 1 裁决（2026-10-14 批量执行，最合理假设）**：**主库即工作副本** —— 「打开库 A/B」= 当场把内容**合并进主库**（`data\newtoys.db`，页面本来就读它），⛔ 不做"切库"（`SqliteDatabase` 路径由 `ConfigStoreService` 固定且与视频工具共库，运行期切径 = 框架层改动 + 跨模块副作用，风险与收益不成比例）。用户描述"打开一个，再打开一个，然后点保存"由此落地为：**两个库的内容合到一起 → 💾 保存 = 把合并结果落成一个 .db 文件**。
- 保存两个去向：**另存为新 `.db`**（默认，文件选择器定位「导入导出默认目录」；目标已存在 → 提示，可覆盖(二次确认) / 追加序号 / 取消）/ **覆盖主库**（= 无需操作，主库已是合并结果；保留此入口无意义 → **不做**，只做另存为）。⛔ 不静默覆盖。
- ⚠️ 合并是**追加语义**（按 path/hash 去重、跳过重复），源库⛔不被修改；合错了靠"减"（勾选删除）回收。

### 移除（－）＝ 选择后删除（🔴 简化版）

- 用户在列表里**勾选**若干行 → 工具条 `🗑 删除选中`（或右键）→ 走既有**软删除**（`status='trashed'`，进回收站，可恢复）。
- ⛔ 不引入 `origin` 列，⛔ 不做"删掉某个库带来的那批"。

## UI 落点

- 工具条「🗄 打开库文件」（现有）语义升级为**打开 / 并入**：选一个 `.db` → **当场合并进主库**（⛔ 只读挂载源库、绝不写源文件；首次打开 = 建立合并基线）。ToolTip 同步改口径。
- 新增 **`💾 保存`**：把当前主库**另存为**一个新 `.db`（默认去向 = 导入导出默认目录；目标已存在 → 覆盖需二次确认 / 追加序号 / 取消）。
- 并入前给一次**确认摘要**（源库路径 + 该库有多少资产 / 位置 + 预计新增 / 跳过），⛔ 不盲合。
- "减"复用 NT-018 / NT-019 已有的勾选 + 删除：工具条「🗑 移入回收站（选中 N）」= 勾选行批量软删除（进回收站可恢复）；永久删除走回收站页。⛔ 本待办不另造删除入口。

## 风险 / 未决

1. ~~**工作副本 vs 直接操作主库**~~ **已裁决（2026-10-14）**：主库即工作副本，合并入主库 + 💾 另存为。理由见上。⚠️ 副作用：合并不可整批撤销（靠"减"逐条回收）—— 用户交互原话已接受此模型（"打开一个，再打开一个，然后保存"）。
2. 合并进来的资产若源路径已不存在，会立刻显示为 `missing` —— 属正常（下次扫描校准）。
3. 大库合并耗时 → 走 `TaskQueue`（NT-015 已有）+ 进度文本，⛔ 不卡 UI。
4. 缩略图 / 元数据（NT-021）不在本项：合并只搬索引，目录里的 `thumbs` 不搬（需要时重新生成）。
5. 另存的新 `.db` 与"主库路径"的关系：另存 = 导出 / 备份语义（⛔ 不自动切过去用）—— 依赖未决 1 的结论。

## 验收清单（草）

- [ ] 打开小库 A（确认摘要 → 合并入主库）→ 再打开库 B → 两库资产 / 位置 / 标签都在列表里
- [ ] `💾 保存` 另存为新 `.db` → 新库能独立打开且内容完整
- [ ] 重复并入同一个库 → 第二次基本全跳过（⛔ 不产生重复资产）
- [ ] 源库文件**未被修改**
- [ ] 勾选若干行 → 「🗑 移入回收站（选中 N）」→ 进回收站可恢复（"减"路径生效）
