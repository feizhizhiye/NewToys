# NT-048 · 修复分屏贴靠**初次失效**（首次拖边不贴靠，最大化一次后恢复）
- 状态：⛔ **已作废**（2026-10-15：现象为**系统级** —— Firefox 同复现 ⇒ 外部纠偏方向错误，⛔ 不复活；第三轮「删零内缩」随官方 CSD 采纳而**定案保留**）
- 优先级：P1
- 关联需求：需求 **§4.1.1 ① / ②**（窗口装饰与窗框、贴靠资格）；§4.1 标题栏
- 依赖：**NT-040**（官方 CSD 路线）｜**NT-041**（样式位补丁已删）｜**NT-042**（已证与 `SetWindowRgn` 无关）
- 创建：2026-10-15 ｜ 更新：2026-10-15

## 背景 / 现象

2026-10-15 用户实测回报：

> 分屏功能，**初次使用不行**，好像**最大化后好了**。

⛔ **关键排除**：该现象是在 NT-042 基准版本上观察到的 —— 该版本 `UseSquareRegionHack = false`，`SetWindowRgn` **全程未生效**。
⇒ 贴靠失效与「矩形窗口区域」无关，**不要往 `ApplySquareRegion` 上找**。

## 🔴 排查顺序（定点验证，⛔ 不许猜着改）

按序验证，每步先**取证**再决定是否动手：

1. **先查窗口样式位在「冷启动 → 首次贴靠前」是否已设全**
   - 关注 `WS_THICKFRAME` / `WS_CAPTION` / `WS_MAXIMIZEBOX` / `WS_SYSMENU`（贴靠资格依赖它们）。
   - 🔴 **诊断只能写文件**（`%LOCALAPPDATA%\NewToys\logs\` 或临时文件）—— ⛔ 无边框自绘窗口的 `Window.Title` **界面上看不见**，⛔ `DwmGetWindowAttribute(33)` **不支持读**（永远 -1）。
   - 对照 NT-041 留下的警告：`ShellView.axaml.cs` 注释明确写了「若日后贴靠再失效，**先怀疑是不是装饰被改回 `BorderOnly` / `None`**」。
2. **查 WndProc 钩子安装时机**：`InstallSnapFrameFix()` 在 `OnOpened` / `OnLoaded` 哪个点装？若在首次布局前装，`ExtendClientArea` 尚未跑完 → 前几帧样式位不完整。
3. **排除自绘抓取区抢事件**（NT-025 / 需求 §4.1）：四边 5px + 四角 10px 的透明热区由 `ElementRole` 标注给系统；确认拖标题栏走的是 `BeginMoveDrag`（而非落在抓取区触发 `BeginResizeDrag`）。
4. **排除全屏遗留态**：`_isFullScreen` / `WINDOWPLACEMENT` 是否残留（NT-044：全屏退出时 Avalonia 用 `SetStyle(_savedWindowInfo.Style)` **整体覆盖样式**）。

⛔ **禁止的做法**：把 NT-041 删掉的 `ApplySnapEligibleStyles` 手工补位抄回来 —— 已证它会与 Avalonia 的重算互相打架（状态变化时它把你补的位抹掉，你再补 → 无谓拉锯）。

## 技术要点 / 约束
- 🔴 圆角来自 `WS_THICKFRAME | WS_CAPTION`，与贴靠资格**绑死** ⇒ ⛔ 别动这两个样式位（动了方角与贴靠一起没）。
- 🔴 Avalonia 每次 `ShowWindow` → `ExtendClientArea()` → `UpdateWindowCornerPreference()` 会重算并回写偏好 ⇒ 补压必须放在 **WndProc 转发处理完之后**（现由 `SnapFrameWndProc` 的 `WM_WINDOWPOSCHANGED` / `WM_SIZE` / `WM_STYLECHANGED` / `WM_SHOWWINDOW` 分支负责）。
- ⛔ **一处一处改、一处一处验**（用户铁律）。本项只解决「贴靠初次失效」，不顺手改别的东西。

## 执行记录（回填）

### 2026-10-15：根因定位 + 修复（一处，待本地验证）

**现象演进（用户两轮实测）**
| 版本 | 现象 |
|---|---|
| NT-042 基准版（`UseSquareRegionHack = false`，全程无 region） | 分屏**初次使用不行**，最大化后好了 |
| NT-042 收尾版（region 恢复生效） | 初次分屏**没间隙，但似乎宽了一点**，之后就正常 |

**🔴 根因（推断，待实测确认）**
- 「贴靠几何」是系统在 **`WM_WINDOWPOSCHANGING` 转发之后**按窗口矩形算的；而此刻窗口上还挂着**按「贴靠前尺寸」建的矩形 region**。
- 有 region 的窗口，系统会**沿用 region 边界**参与几何计算 ⇒ 初次贴靠被旧（更宽的）region 带偏。
- region 要到随后的 `WM_WINDOWPOSCHANGED` → `ReassertWindowChrome` 才更新 ⇒ 完美解释「**第一次**偏宽 / 不行，**之后**就正常」。
- ✅ 这也解释了为什么「关掉 region 时反而是『初次不行』」：无 region 时系统按标准窗口几何贴靠，但贴靠后 Avalonia 的 `ExtendClientArea` 重算 + 我们零内缩 → 首次那一轮几何没收敛；两种状态表现不同，但同属「首次几何未收敛」这一族。

**修复（只改 `src/Shell/Views/ShellView.axaml.cs` 一处逻辑）**
- 新增 `WM_WINDOWPOSCHANGING`（`0x0046`）常量。
- 新增 `ClearSquareRegion(hwnd)`：**只摘不套**（`SetWindowRgn(NULL)`）。
- `SnapFrameWndProc` 里**转发之前**插入：
  ```
  if (msg == WM_WINDOWPOSCHANGING && lParam != IntPtr.Zero) {
      // WINDOWPOS: hwnd(ptr) / hwndInsertAfter(ptr) / x / y / cx / cy / flags —— flags 在尾部
      var winposFlags = Marshal.ReadInt32(lParam, IntPtr.Size * 2 + 16);
      if ((winposFlags & (int)SWP_NOSIZE) == 0)   // 尺寸会变（贴靠 / 缩放）→ 先摘 region
          ClearSquareRegion(hWnd);
  }
  ```
  ⛔ **只在尺寸会变时摘**：纯拖动窗口（`SWP_NOSIZE`）不动 region，否则拖动全程无 region → 圆角闪。
- 摘掉后由既有的 `WM_WINDOWPOSCHANGED` → `ReassertWindowChrome` 按**新尺寸**重新套上，无需新增恢复逻辑。

**需本地验证（手工回归清单）**
1. `pwsh -File .\scripts\build.ps1` → 编译通过。
2. **冷启动 → 首次**拖到左 / 右边缘贴靠：**宽度与第二次贴靠一致**（⛔ 不再"宽一点"）、无间隙。
3. 二次 / 三次贴靠：仍正常（回归）。
4. 拖动窗口（不改尺寸）：方角不闪、无圆角复发。
5. 拖边框缩放：无内容裁切、缩放结束方角恢复。
6. 最大化 / 还原 / 全屏进→`Esc`出：无露边、无裁切、方角保持。

### 2026-10-15：第二轮（第一轮实测**无效**，换打法）

**实测反馈**：摘 region 那版编译后，**首次分屏不收敛仍在** ⇒ 「旧 region 参与贴靠几何」被证伪（`ClearSquareRegion` 逻辑本身无害，保留）。

**新假设**：问题不是 region，而是**尺寸期望不一致** —— 启动时 `ApplyWindowFrame` 用 `SetWindowPos` 直接设外框（绕开 Avalonia），而我们在 `WM_NCCALCSIZE` 里把 Avalonia 算出的客户区改回「= 外框」→ 它记的窗口尺寸与实际外框有固定差；首次贴靠时它按自己那份记录回写一次 → 窗口脱离系统给的贴靠矩形；随后两边同步 ⇒ 之后正常（与「第一次偏、之后正常」完全吻合；量级线索 = v3.29 注释里的 16px）。

**修法（⛔ 不依赖任何"差多少 px"的经验值，只改 `src/Shell/Views/ShellView.axaml.cs`）**
- **方案 A（期望比对）**：`WM_WINDOWPOSCHANGING` 抄下 WINDOWPOS 的 x/y/cx/cy 作为「系统要求的矩形」（`NOMOVE`/`NOSIZE` 时用当前外框补齐）；`WM_WINDOWPOSCHANGED` **转发之后**比对实际外框，偏离（≤64px，>64 视为最大化/全屏状态切换、不动手）就 `SetWindowPos` 纠回 + `ReassertWindowChrome` 重套 region/圆角。正常拖动 / 缩放 / 最大化天然相等 → 零副作用。
- **方案 B（屏幕几何兜底）**：若偏差是 Avalonia **自己再发一次** `SetWindowPos` 造成的，方案 A 的基准会被一起带偏（基准 == 实际 → 判不出）⇒ 追加按屏幕自检：非最大化/全屏 **且** 高度精确 == 工作区高 **且** 左或右边缘贴住工作区 **且** 宽度接近但不等于「半屏 / 1/3 / 2/3」之一（容差 64）→ 纠到该标准宽度。`MonitorFromWindow` + `GetMonitorInfo`（新增两个 P/Invoke + `MONITORINFO`）。
- **基准锁定**：`ApplyWindowFrame` 设完外框后把该矩形钉成基准并锁 300ms（`_frameLockUntil`），期间 `RememberWantedFrame` 不覆盖 —— 否则启动恢复的尺寸也会被 Avalonia 回写顶偏（顺带防「每次启动变大一圈」复发）。
- **震荡闸门**：500ms 内最多纠 3 次（`_correctionBurst`），防「我们纠回 ↔ Avalonia 再回写」的同步消息递归；`_inSnapCorrection` 防重入。

**需本地验证（同上一轮 1~6，重点 2）**
1. `pwsh -File .\scripts\build.ps1` → 编译通过。
2. **冷启动 → 首次**拖到左/右边缘 → 贴靠成功且**宽度与第二次一致**（⛔ 不再偏宽）。
3. 手动拖边框缩放到「全高 + 贴边 + 宽度接近半屏但不等」→ ⚠️ 会被纠成半屏（已知取舍，确认可接受）。
4. 普通拖动 / 缩放 / 最大化 / 全屏 → 无被"拽回去"的异常。

### 2026-10-15：⛔ 作废（窗口装饰路线反转）

**用户拍板**：NT-034 之后「向官方方案靠拢」的重构（NT-039~048）**无法完美实现** ⇒ 按 **NT-034 基线**重新实现当前 UI。

**本项处置**（现象属官方 CSD 路线特有，路线一换即消失）：
- 第三轮「删 `WM_NCCALCSIZE` 零内缩、让 Avalonia 官方接管客户区扩展」→ 🔴 **定案保留**（2026-10-15 官方 CSD 采纳后，客户区扩展归框架；不再自接管）。
- 第一 / 二轮两套纠偏（`ClearSquareRegion` / `RememberWantedFrame` / `CorrectSnapFrame` / `CorrectSnapGeometry` / `MONITORINFO` + `MonitorFromWindow` / `GetMonitorInfo` / `ApplyWindowFrame` 的基准钉位 / `WM_WINDOWPOSCHANGING` 分支）→ **全部删除**：它们本质是给官方路线「Avalonia 记账尺寸 vs 实际外框差 ~8px」做的外部补偿，且已被「首次偏宽 = 系统行为」的取证否掉。
- **结论留档**：贴靠几何**归框架 / 系统** —— 首次偏宽是系统行为（Firefox 同复现），⛔ 任何外部纠偏都不做。

**定案验证（手工回归清单）**：冷启动首次拖边贴靠 / 二次贴靠 / 拖拽 / 边框缩放 / 最大化还原 / 全屏进出，六项均需重验（**贴靠态 1px 残差预期仍在 = 系统级**）。

### 2026-10-15：用户补充取证（第三方窗口复现 ⇒ 系统级行为）

- 🔴 用户实测：**切换浏览器做分屏，同样「第一次宽一些、第二次就好了」** ⇒ 该现象是 **Windows 贴靠自身行为**（首次按动画中间几何给尺寸 / 第二次校准），**与本项目窗口层无关**。
- 🔴 **Firefox 进一步复现（决定性）**：**贴左半屏 → 右边缘溢出重叠；贴右半屏 → 与屏幕边有 1px 间隙** —— 与 NewToys 完全一致，且**左右不对称**。
  ⇒ 该 1px 是**系统级取整 / 动画帧落位**的结果（半个工作区宽出现 .5px 时的取整方向差），⛔ **不是** `SetWindowRgn` / 零内缩 / 样式位的问题。
- ⇒ **三个结论**：① NT-048 作废判断成立；② 其「贴靠几何外部纠偏」这套思路**方向就是错的**（在系统的正常行为上打补丁）⇒ 删除正确，⛔ 别再复活；③ 贴靠态 1px 残差**接受为行业固有**（与今日调研的 AtomUI / PyQt-Frameless-Window 结论一致）。
- 📌 若要验证「到底是不是我们这边」：**同屏同位**把 Firefox 与 NewToys 各贴一次，看缝的边与宽度是否一致 —— 本次已按此法判定。
