## 背景 / 目标

**拆成两页**（2026-10-19 用户定调）：

| 页 | Key / 标题 | 形态 | 职责 |
|---|---|---|---|
| 管理页 | `web-scrape` / 「抓取规则」 | **标准列表页**（⛔ 不动 `ListPageSkeleton`） | 规则目录：新建 / 删除 / 启用 / 导入书源 / 导出 / 重读 / 搜索；双击或右键 `✏ 编辑规则` → 跳编辑器 |

🔴 **新开一页顺带把框架例外消掉了**：新页本来就不是列表页，自绘属正常（`web-http` 先例）—— ⛔ 不需要改 `ListPageSkeleton`、⛔ 不需要改 340px 详情卡。

## 规则载体

`<DataDir>\web-tools\rules\<规则集名>.py` —— **一个文件 = 一条规则集**（手改 / 备份 / 分享都靠它）。

```python
SOURCE = {"name": "示例站", "base": "https://ex.com", "encoding": "utf8",
          "search_url": "/search?q={key}&p={page}", "header": {}}

RULES = [
    ("title", "css:.name@text"),
    ("url",   "css:a@href | abs"),
    ("date",  "css:.time@text | regex:(\\d{4}-\\d{2}-\\d{2})"),
]

# 规则表达不了时才用：search / detail / toc / content 四个可选函数
```

- helper `sel` / `abs_url` / `clean` / `http` 住 Python 侧 `tools/rulekit.py`（**C# 零解析逻辑**）。
- `<DataDir>\web-tools\cache\<规则集名>\*.html` 存 HTML 缓存，留最近 10 份，⛔ 不进备份。
- DB 只存：启用状态 / 最后运行 / 列宽偏好。

### H3 阶段模型（🔴 覆盖性来源，**不是分类**）

统一抽象：**每个 stage 的返回只有两种——「行列表 rows」（继续下一级）或「产物 artifact」（终止）**。

| stage | 签名（示意） | 返回 |
|---|---|---|
| `list` | `(key, page, url) -> rows` | 目录 / 条目行 |
| `detail` | `(row) -> row'` | 行增强（可选） |
| `toc` | `(row) -> rows` | **子级链接**（书籍章节） |
| `content` | `(row) -> artifact \| rows` | 正文 / 文件清单 / 再下一级 |
| `next` | `(html) -> url` | 翻页原语，任何 stage 可用 |

**UI 只有两个动作**，与「两阶段」按钮一一对应：

- **「抓链接」** = 从起始 URL 跑 `list`（→`detail`→`toc`…）直到产出 rows 为止，**多级自动串联**；
- **「下载」** = 对选中行跑 `content`（单条 = 试下载，多条 = 批量下载）。

⇒ 「两阶段」是**动作语义**，⛔ 不代表流水线固定两级：书籍 = `list→toc→content` 三级照样跑，图片站 = `list→content` 两级，单页文字 = `content` 一级。深度由脚本 `# stages:` 声明，⛔ UI 不硬编码。

### H4 产物形态（决定下载器，⛔ 不由分类决定）

| `content` 返回 | 下载器 | 落地 |
|---|---|---|
| `{"text": …}` | 文本拼接 | `downloads/<脚本>/<条目>/正文.txt` |
| `{"files":[{"url":…,"name":…}]}` | 逐个取二进制 | `downloads/<脚本>/<条目>/<name>` |
| `{"rows":[…]}` | 递归当链接（进入下一级，不下盘） | — |
| 空 / 无 `content` | ⛔ 该脚本只到目录级（不显示下载按钮） | — |

**分类的职责收窄为三件事**：① 列表展示分组与筛选；② AI 写脚本时的提示（Books 期望 text，图片/视频/文档期望 files）；③ `content` **未声明形态时的缺省猜测**（`image/video/doc`→files，`book`→text）。实际行为**永远以 `content` 返回为准**。

### H5 覆盖性分析（用户问：这样分类能否覆盖所有需求）

**结论：分类覆盖不了，覆盖靠「stage 链 × 产物形态」二维模型；分类只是索引标签。** 典型场景落位：

| 需求 | stage 链 | 产物 | 覆盖 |
|---|---|---|---|
| 只要目录（比价/聚合/监控清单） | `list` | none（导出 CSV/JSON） | ✅ |
| 只要 URL 列表（喂别的工具） | `list`（url 字段） | none | ✅ |
| 书籍（目录→章节→正文） | `list→toc→content` | text | ✅ |
| 图片/壁纸站（列表页→原图） | `list→content` | files | ✅ |
| 视频/音频站 | `list→content`（可再 `detail` 取真实地址） | files | ✅ |
| 文档/电子书/压缩包站 | `list→content` | files | ✅ |
| 单页文字抽取（无目录） | `content` | text | ✅ |
| 分页长列表（搜索/分类翻页） | `list` + `next` | none | ✅ |
| 目录分页 + 正文分页 | `list`+`next`、`content`+`next` | text | ✅ |
| 详情页增强（先 detail 再 content） | `list→detail→content` | text/files | ✅ |
| 论坛/帖子（列表→楼层→图片） | `list→toc→content` | files | ✅ |

**明确不覆盖（范式边界，与分类无关）**：

1. **JS 渲染 / SPA**（parsel 只吃静态 HTML）—— 最可能踩的硬性边界。
2. 登录态 / POST 表单 / 验证码 / 付费内容。
3. **发现式整站爬取**（URL frontier / 未知链接递归）—— §2.2 L3 封顶。
4. 定时监控 / 变更检测 / 增量告警（changedetection 类）。
5. 结构化导出到 DB / Excel（只做 CSV/JSON）。
6. 富文本排版 / EPUB / 阅读器。
7. 大文件断点续传（只做整文件重下 + 已存在跳过）。
8. 多站点聚合在一个脚本（一个脚本 = 一个站点；多站 = 复制脚本改 `base`）。

⇒ 若某需求落进上表：**不是分类不够，是范式边界**。判定流程 = 先问「能不能静态 HTML 取到」（1、2）→ 再问「是不是已知结构链路」（3）→ 剩下的基本都能用 stage 链表达；只有需要**新 stage 类型**（如「合并多页 rows」「按规则过滤行」）时才是模型扩展，成本很低（加一个约定名 + 引擎分支）。

2. 脚本头 `# artifact: text|files|none`——AI 显式声明（契约推荐写）；

## J. 预设脚本库（用户问：用集合机制 + 预设脚本，能否兼容绝大多数网站）

### J1 可行性判断

**架构层：✅ 成立**——脚本就是**可插拔的「中间段」（解析段）**：UI（面板）、引擎（抓 + 求值）、存储（runs/downloads）全不动，换脚本 = 换段。这正是 H3 stage 模型的价值。

**覆盖层：⚠️ 有条件成立**——「换段就行」的前提是**那段已经存在**。段从哪来决定覆盖率：

- 段 = 协议/标准接口 ⇒ 一次写好，吃一大片（稳）；
- 段 = 某 CMS 主题的选择器 ⇒ 主题一换就废（脆）；
- 段 = 具体站点规则 ⇒ 改版即废（负债）。

⇒ **结论：值得做预设库，但预设的是「协议 / API 适配器」，⛔ 不是站点规则库。**

### J2 定位（🔴 一句话）

**优先预设「结构化接口型」脚本，其次才是 HTML 选择器型**。理由：API/标准格式返回结构化数据，**不受主题改版影响**，命中即长期有效；HTML 选择器则随主题漂移。

### J3 预设清单（草案）

| 级 | 预设 | 入口 | 字段 | 覆盖 |
|---|---|---|---|---|
| **P0** | `rss` | `/feed` `/rss.xml` `/atom.xml` | title/link/date/summary | 所有提供 feed 的博客 / 新闻 |
| **P0** | `opds` | `/opds` 或站方给的 catalog URL | 书名/作者/**下载链接**（files） | 电子书站（书籍类天然标准） |
| **P0** | `sitemap` | `/sitemap.xml`（含 index 递归一级） | URL 清单（none） | 只要链接的场景 |
| **P0** | `wp-json` | `/wp-json/wp/v2/posts?search={key}&page={page}`（`json:` 规则） | title/link/date/excerpt | WordPress 占比极高，**不受主题影响** |
| **P0** | `mediawiki` | `api.php?action=query&list=search&srsearch={key}&format=json` | 标题/链接 | MediaWiki 系（含众多 wiki 站） |
| **P0** | `links`（**兜底**） | 任意页 + 可选容器选择器 | 所有 `a[href]` + 文本 | 长尾站「只要链接」的保底 |
| **P0** | `images`（**兜底**） | 任意页 + 可选容器选择器 | 所有 `img[src]`/`data-src`（files 产物） | 图站 / 壁纸站的保底 |
| P1 | `discourse`（`.json`）/ `ghost` / `static-blog`（Hugo/Hexo/Jekyll：`h2 > a` + 日期）/ `discuz` / `forum`（列表→楼层→图片） | — | — | 主题差异会影响，命中率中等 |
| ⛔ 不做 | **具体大站规则库**（某某小说网 / 某某图站） | — | — | 改版即废 + 维护负债 + 合规风险 |

### J4 集合机制的真正用法：**一次抓页，多脚本试跑，分节对比**

ScriptManager 集合 =「一组采集器一起跑、分节展示」⇒ 爬虫面板照搬即：**选一个 URL，勾 N 个候选预设（或整个集合），跑一遍，每节显示命中数/字段完整度，用户挑有数据的那个 → 「另存为我的脚本」**。

🔴 **成本近乎为零**：多个脚本只是对**同一份 HTML** 求值（抓一次即可），⛔ 不是 N 次请求。这是「多预设试跑」能成立的技术前提。

- 选优判据：**条数 > 0 且必填字段非空率最高**，⛔ 不能只判「非空」（防止抓到导航/广告链接的 false positive）。
- 未选中预设的节默认折叠（照信息面板的节折叠）。

### J5 探测辅助（低成本高收益）

新建脚本时输入 URL → 后台按顺序试（≤7 个请求，串行 + 短超时 + 复用）：

`/feed` `/rss.xml` `/atom.xml` `/sitemap.xml` `/wp-json/wp/v2/posts?per_page=1` `/api.php?action=query&meta=siteinfo&format=json` `/opds`

第一个**能解析出条目**的 ⇒ 推荐对应预设（⛔ 不能只看 200：很多站 404 也返回 HTML 页）。推荐结果只是**提示**，⛔ 不自动替用户决定。

### J6 覆盖性诚实估计

| 站点类型 | 命中路径 |
|---|---|
| 提供 feed / OPDS / sitemap | 预设**一击命中**（新闻、博客、电子书站覆盖可观） |
| WordPress / MediaWiki / Discourse 等有 API | **API 型预设稳定命中**（不受主题影响） |
| 主流 CMS 但只有 HTML | P1 预设部分命中；不中 ⇒ 走 AI 现写（主路径不变） |
| 长尾 HTML 站 | 兜底预设（links/images）能应付「只要链接/图片」；复杂字段靠 AI 写 |
| SPA | 有后端 API ⇒ API 型适用；否则**整体不适用**（parsel 只吃静态 HTML，不变边界） |

⇒ 预设是**覆盖率放大器**（吃掉高频通用部分），⛔ 不是万能解；长尾仍归 AI 现写这条主路径。

### J7 风险与对策

1. **预设失效**（CMS 升级 / 接口变更）⇒ 只收稳定协议与官方 API；用户拿的是**副本**（可改），失效走 `📋 复制诊断` → AI 修，与自制脚本同一回路。
2. **false positive**（抓到导航/广告）⇒ J4 的选优判据 + 试下载验证（期②）。
3. **Seeder 反复种植**：随包预设落 `data/web-tools/presets/`（或 rules 目录）需「已删不再种」标记 —— 沿用既有 seeder 的 `.seeded` 做法，🔴 注意导出 zip 会带 `.seeded`（导入白名单必须跳过它，且**先判 `../`、绝对路径**再跳过，见 NT-067 坑）。
4. **选择困难** ⇒ 探测（J5）+ 分类筛选；预设数量控制在 ~10 个。
5. **维护责任**：每个预设必须**在契约下实测跑通**才入库（纳入验收）；由 AI 写 + 人工验，⛔ 不入库未验证的。
6. **体积 / 合规**：纯文本 `.py`，体积可忽略；⛔ 不内置具体站点规则。

### J8 分期建议

- **期①末**（或紧接的小批）：P0 七个预设 + 随包 + Seeder + 「新建时选预设」+ 探测（J5）。
- **期②**：多脚本试跑分节对比（J4）+ 试下载验证选优。
- ⛔ 不单独立项一个「预设库」大卡：它是脚本库的内容扩充，不是新机制。

## K. 抗变更（规则失效）方案（用户问：强制用 XPath 能否解决选择器随主题/样式失效）

### K1 强制 XPath 的评估：**不能解决，⛔ 不强制**

| 维度 | CSS | XPath |
|---|---|---|
| 依赖类名 | 是 | **同样是**（`//div[@class='x']` 一样断） |
| 依赖嵌套层级 | 是 | **同样是** |
| 按文本选择 | ⛔ 标准 CSS 无 `:contains` | ✅ `//a[contains(text(),'下一页')]` |
| 父/兄弟/轴 | ⛔ | ✅（`..`、`following-sibling::`） |
| 位置索引 | 部分 | ✅ |
| 可读性 / AI 熟练度 | 高 | 中（长、易写错） |

⇒ 换主题时类名与结构一起变，**XPath 一样断**；强制只会牺牲可读性与 AI 产出质量。

**XPath 唯一不可替代的能力 = 按文本内容定位**——而「下一页 / 下一章 / 目录」这类**功能文本几乎不随改版变化**，这才是抗变更的真锚点。⇒ 用法是「**需要文本锚时才用 XPath**」，⛔ 不是全局强制。

**顺带否定正则**：正则跑在原始 HTML 文本上，换行、属性顺序、空格一变就断，**比 CSS 更脆**；只配做「字段内二次提取」（如从 `2026-10-20 12:00` 里截日期），⛔ 不做主力定位手段。

### K2 抗变更的真正杠杆 = **锚点稳定性分级**（🔴 写进契约，AI 按此顺序写）

| 稳度 | 锚点 | 示例 | 说明 |
|---|---|---|---|
| ❌ 禁用 | 绝对位置 | `/html/body/div[3]/div[1]` | 一改就断，契约明令 ⛔ |
| 1 脆 | 主题类名 | `.post-title` / `#main` | 换主题即废 |
| 2 中 | 语义标签层级 | `article h2 a` / `main ul li a` | HTML5 语义标签比类名稳 |
| 3 较稳 | **URL 模式** | `a[href*="/chapter/"]` | 路由由后端定，改前端常保留 |
| 4 稳 | **功能文本** | `//a[contains(text(),'下一页')]` | 功能文案几乎不变 |
| 5 最稳 | **协议 / API** | `rss` / `wp-json` / `opds` | 与渲染完全解耦（J 节） |

**推荐写法**：一条规则写**多个候选**，按稳度从高到低排列，用现有 `||` 取第一个有结果的：

```
("next", "text:下一页 || url:/next/ || css:a.next@href")
```

⇒ 抗变更不是靠单一语法，而是「**稳锚点优先 + 多候选回退**」——`||` 机制**已经有了**，只需在契约里规定排序纪律。

### K3 引擎小改：三个语义操作符（成本低，约 20~30 行 Python）

| 操作符 | 含义 | 转写（parsel 已支持 xpath） |
|---|---|---|
| `text:下一页` | 按可见文本找元素 | `//*[contains(normalize-space(.), '下一页')]`（优先 `a`） |
| `link:下一章` | 按链接文本找 `<a>` | `//a[contains(normalize-space(.), '下一章')]` |
| `url:/chapter/` | 按 href 片段找 `<a>` | `//a[contains(@href, '/chapter/')]` |

- 比裸 XPath 好写、好读、好教 AI；与 `css:`/`xpath:`/`json:` 并列，⛔ 不改现有语法。
- 契约新增一条硬禁令：**⛔ 禁止绝对位置路径**（`/html/body/...`、`div[3]` 连续索引）。

### K4 失效后的「自愈」辅助（分两步，成本递增）

| 步 | 内容 | 成本 | 期 |
|---|---|---|---|
| **诊断给候选建议** | 某字段跑空时，诊断里附：① 页面里 `<a>` 总数与高频 href 模式（如「存在 12 个 `/chapter/` 链接」）② 原规则用的文本锚是否仍在页面里 ③ 建议改用哪条 | ~30~50 行 | 期①末 |
| **结构推断**（EasySpider 式） | 用户标一个样本条目 → 找含它的**最小重复容器** → 生成基于「重复结构 + 标签序列」的选择器（⛔ 不用类名） | ~50~100 行 | 期② / 二期 |

⇒ 把「规则失效 → 人肉重看源码」变成「诊断里直接给候选，选一个即可」，这是抗变更的**运维侧**解法，与 K2 的**写法侧**解法配套。

### K5 结论

1. ⛔ **不强制 XPath**（治标不治本 + 牺牲可读性）；XPath 只用于「文本锚 / 轴 / 位置」场景。
2. ✅ 真正的三层抗变更：**L1 数据源**（feed/API，J 节已定）→ **L2 锚点**（稳度分级 + `||` 多候选 + 三个语义操作符）→ **L3 失效**（诊断给候选建议 + 二期结构推断）。
3. 成本：K3 约 20~30 行引擎改动 + 契约文档；K4 第一步约 30~50 行 ⇒ 都属小改，可并进期①末或紧接一批。

2. 失效候选建议（K4 步 1）是否同期做？
3. 结构推断（K4 步 2）列二期，是否同意？

## L. 用户新设想：**调试集合（三段装配）** —— 脚本从「整站」降为「一段」

> 设想：把命令检验页改成**调试集合**——启动一个**搜索脚本** → 拿着 HTML **手动选目录解析脚本** → 再**选正文解析脚本**（共三段）→ 跑通后在抓取面板启用批量下载。论点：**前期备好脚本，后期越来越简单**。

### L1 定位变化（🔴 与 H 节的载体粒度不同，H3 的 stage 语义不变）

| | 现行（H 节） | 新设想 |
|---|---|---|
| 脚本粒度 | 一个 `.py` = **一个站点**（内含 `stages: list,toc,content`） | 一个 `.py` = **一段**（搜索 / 目录 / 正文） |
| 链路组装 | 写死在脚本里 | **运行时手动选**，存成流水线配置 |
| 复用 | 整站脚本复制改 base | **每段跨站复用**（一个正文脚本给 N 个站用） |
| 产物 | 脚本自带 | **`flows/<名>.json`**：三段脚本 + URL 模板 + 参数 |

### L2 评估：**采纳，确实更好**（理由）

1. **复用率跃升**：正文脚本（通用小说正文 + 文本锚翻页）能给上百个站用；目录脚本同理 ⇒ 边际成本递减，你的判断成立。
2. **组合覆盖**：M 个搜索 × N 个目录 × K 个正文 ⇒ 组合数远大于整站脚本数。
3. **调试粒度对**：一段一段跑、HTML 在手里，比整链路黑盒跑好定位。
4. **契合 AI 范式**：AI 只写"某一段的小脚本"，任务小、成功率高、可单测。
5. **契合集合机制**：集合 = 一组脚本的组合，这就是它的本来用法。

⚠️ 「越来越简单」成立的**前提**：脚本库要有**质量门槛与去重**（入库实测跑通 + `# works:` 适用站点 + 说明），否则攒一堆半可用脚本后，**选择成本会反超收益**。

### L3 必须先定的三件事（否则装配不起来）

| # | 事项 | 设计 |
|---|---|---|
| 1 | **段间契约** | 入口/中间段输出**必须含 `url`**（下一级要抓的地址）；`title` 为推荐保留字段；其余字段自由。终段输出 artifact（`text`/`files`）。缺 `url` ⇒ 诊断明确指出「第 N 段输出没有 url 字段」⛔ 不静默 |
| 2 | **角色声明 + 候选过滤** | 脚本头 `# role: list\|toc\|content\|pipeline`（🔴 与 H/I 节的 `# stages:` 改口径：那是"本脚本含哪些段"，新模型下多数脚本只扮演一段）；面板按**当前槽位的 role** 过滤候选，⛔ 不把全部脚本列出来 |
| 3 | **试跑推荐提前** | J4「一次抓页、多脚本求值、分节比命中数」**从期②提到期①**——它是"手动选哪段"的唯一可用判据，没有它用户只能盲选 |

### L4 配套改动清单

- 脚本头新增：`# role:`、`# works: 域名`（适用站点，多个用逗号）、沿用 `# category:` / `# desc:`。
- 新增 `Models/FlowConfig.cs` + `Services/FlowService.cs`：`<DataDir>\web-tools\flows\<名>.json`（entry/toc/content 脚本名 + URL 模板 + 参数 + 备注），⛔ 不新开 DB 表。
- 目录页：加「角色 ▾」筛选；**删除脚本时引用检查**（被 N 条流水线引用 ⇒ 提示 ⛔ 不静默删）。
- 调试集合页（原 `web-rule-editor` 重构）：左 = 三段槽位（下拉选脚本，按 role 过滤 + 试跑推荐排序）／中 = HTML + 结果／右 = 选中段脚本的**表达式检验**（I1 的命令检验降为子功能）+ 错误回显；底栏「💾 保存为流水线」。
- 面板 `web-crawl`：读 flow 跑批量下载（期②）。
- 引擎：段间传参（`row` + 该行 url 抓到的 `html`）；**urljoin 的 base = 当前页 URL**（⛔ 不是站点根）。
- 兼容：无 `# role:` 的老脚本按 `pipeline`（整站）处理，⛔ 不强拆。

### L5 技术风险（按严重度）

1. 🔴 **段间契约不严 → 链路断**：字段名/相对 URL/缺失 url 都会让装配失败 ⇒ 契约写死 + 诊断显式报错。
2. 🔴 **候选太多 → 选择成本**：必须靠 role 过滤 + 试跑排序 + `# works:` 提示；脚本库要治理（入库验收 + 去重）。
3. 🟠 **流水线引用完整性**：改/删脚本可能弄坏已保存的 flow ⇒ 引用计数 + 删除提示 + 打开 flow 时校验脚本仍存在。
4. 🟠 **试跑误判**（抓到导航/广告却"有数据"）⇒ 判据 = 条数>0 **且**必填字段非空率最高（J4 已定）。
5. 🟡 **三段不够**：书籍实际是 搜索→详情→目录→正文 ⇒ 中间槽位**允许连选多个**（默认三段），⛔ 不硬编码深度。
6. 🟡 **调试阶段误跑全量** ⇒ 调试只跑**样本 1 条**（等同试下载），⛔ UI 不提供"全部跑"入口。
7. 🟡 **老整站脚本兼容**：保留 `pipeline` 角色即可，成本低。
8. 🟢 请求放大：试跑共用同一 HTML（成本≈0）；下钻每条目 1 次请求 ⇒ 走并发/间隔（脚本头配置，期②）。
9. 🟢 页面复杂度：调试页要做「槽位 + 试跑 + 表达式检验」三件事 ⇒ 布局按三段式切，⛔ 不塞第四块。

### L6 待拍板

1. 采纳 L 设想 ⇒ **脚本定义从「一个站点」改为「一段」**，H/I 节的 `# stages:` 改为 `# role:`（老脚本按 `pipeline` 兼容），是否确认？
2. J4 试跑推荐**提前到期①**（作为选段的判据），是否同意？
3. 三段固定 vs 中间槽位可连选多个（默认三段）？
4. 流水线配置是否需要「版本/备注」字段，或先做最简（三段名 + URL 模板）？

## M. 链路段位规范化（用户确认逻辑：**可以增减**）

> 用户表述：输入网址 → 看 HTML 找搜索方式 → ① 搜索脚本 → ② 详情页脚本 → ③ 目录解析 → ④ 正文链接解析 → ⑤ 下载脚本。问是否为此逻辑、可否增减。

### M1 结论：逻辑成立，规范为 **五段 + 一个附加原语**

| # | 段 | 输入 → 输出 | 必须 | 何时**需要**脚本 |
|---|---|---|---|---|
| 0 | `probe` 探测 | URL → 候选（feed/wp-json/sitemap/…） | 否 | ⛔ 内置（J5），⛔ 不写脚本 |
| 1 | `entry` 入口/搜索 | URL / 关键词 → `rows`（**含 `url`**） | ✅ 是 | 几乎总是 |
| 2 | `pick` 条目筛选 / 详情 | `rows` → 选中 1 行（或增强字段） | 视场景 | 🔴 **通常人工点选即可**（同名书消歧）⇒ ⛔ 不必写脚本；只有批量自动化（按作者/年份匹配）才要规则 |
| 3 | `toc` 目录 | 详情页 HTML → `rows`（章节，含 `url`） | 书籍类要；图片/文档类常无 | 站点有目录页时 |
| 4 | `content` 正文 / 资源 | 章节 HTML → `text` / `files` | ✅ 是 | 总是 |
| 5 | `save` 落盘 | `text`/`files` → 本地文件 | ✅ 是（**内置**） | ⛔ **内置下载器**（并发/限速/去重/续跑/命名/进度/取消）；仅「二次请求取真实地址 / 解密 / 合并分片」才写脚本 |
| 附 | `next` 翻页 | HTML → 下一页 URL | 可选 | 🔴 **挂在各段上的参数**（文本锚 / URL 模式），⛔ 不是独立段 |

### M2 三个必须厘清的点（用户的表述里有歧义）

1. **「详情页脚本」多数情况不需要**：搜索结果行里通常已带详情页 URL ⇒ 直接进，⛔ 不必再写一段。只有"要进详情页取额外字段/校验是否正确的书"时才需要（此时它就是 `pick` 的可选规则）。
2. 🔴 **目录型 vs 链式型**（用户未区分，两种都要支持）：
   - **目录型**：有目录页，`toc` 段**一次取全**章节列表 ⇒ 可勾选范围批量下；
   - **链式型**：正文页只给「下一章」链接，无目录页 ⇒ **没有 `toc` 段**，靠 `content` + `next` **逐页跟进**，目录是**边跑边累积**出来的。
   ⇒ UI 上 `toc` 槽位**留空 = 链式模式**；批量下载时从起点跟到上限/文末。
3. **「下载脚本」默认 ⛔ 不写**：下载是通用能力（并发/限速/去重/续跑/命名/取消/进度），脚本化会重复实现且丢掉取消与错误处理——与既定纪律「写操作 ⛔ 不脚本化」一致。

### M3 增减规则（按站点裁段，**最小集 = `entry` + `content`（+ 内置 `save`）**）

| 站点类型 | 链路 |
|---|---|
| 书籍（有目录） | `entry → pick(人工) → toc → content(+next) → save` |
| 书籍（只有下一章） | `entry → pick(人工) → content(+next 链式) → save` |
| 图片 / 壁纸站 | `entry → pick(可选) → content(files) → save` |
| 文档 / 资源站 | `entry(sitemap 也行) → content(files) → save` |
| 单页文字 | `content → save` |
| 只要清单 / 监控 | `entry → 导出 CSV/JSON`（无 save） |

⇒ **槽位 UI 一律显示"可选"，允许留空跳过**；⛔ 不为每段强制脚本。

### M4 对 L 节设计的修正

- L 节写的是「三段槽位」，M 节修正为 **五段槽位 + `next` 参数**，其中 `pick` 默认人工、`save` 默认内置 ⇒ **真正需要用户选脚本的通常只有 2~3 个槽位**（entry / toc / content）。
- `flows/<名>.json` 字段相应扩：`entry` / `pick`(可选规则) / `toc`(可空) / `content` / `save`(内置或脚本) / `next`(各段翻页参数) / `url` 模板 / 备注。

### M5 待拍板

1. 五段命名是否照此定（`entry` / `pick` / `toc` / `content` / `save` + `next`）？
2. 链式型（无 toc、`next` 跟到上限）是否与目录型同批做，还是先只做目录型？
3. `pick` 是否**默认人工点选**（⛔ 不做匹配规则），仅期②再考虑自动化？

## N. 「自动判断下一阶段」= 把集合塞回一个脚本吗？（用户追问）

### N1 承认：**表达力上基本等价**

调度脚本（if 分支选子脚本）与整站单脚本（内含 stages + 分支）**都是 Python，图灵完备 ⇒ 复杂度不会消失，只会搬家**。「自动判断」没有消灭 if 线，只是把 if 从"整站脚本里"搬到"调度脚本里"。

### N2 但「搬到哪」有意义（组织方式差异是真实价值）

| 维度 | 整站单脚本（if 线全在内） | 调度器 + 段脚本 |
|---|---|---|
| 复用 | ⛔ 整份复制 | ✅ 段可跨站复用 |
| AI 写 | 一次写长文，易错 | 一次写一段，成功率高 |
| 定位 | 整份重跑 | **段级隔离**，哪段挂了一眼可见 |
| 改版 | 整份改 | 只改失效那段 |
| 调度逻辑 | 散落在代码里难读 | **显式**（flow 配置可见可改） |
| 失败模式 | 一处错全崩 | 段级失败不连坐 |

⇒ 真正的收益是「**复杂度显式化 + 可复用 + 可隔离**」，⛔ 不是「自动化」。

### N3 自动化分三档，价值差很大

| 档 | 做法 | 要不要写脚本 | 价值 |
|---|---|---|---|
| **A 试跑推荐** | 一次抓页 → 候选脚本全求值 → 按命中数/字段完整度排序推荐 | ⛔ **内置能力**（J4，零脚本） | 🔴 最高：解决「选哪个」的盲区 |
| **B 静态编排** | flow 配置里声明 `toc: xxx.py`、`content: yyy.py` | ⛔ 配置，不是代码 | 高：显式、可改、可读 |
| **C 动态调度脚本** | 脚本读 HTML → if 判断 → 调不同子脚本 | ✅ 要写 | ⚠️ 只在**同站内版式不一**（多模板/AB/章节结构不一致）时才值 |

⇒ **主路径 = A + B**；**C 是逃生舱**，⛔ 不做默认。

### N4 🔴 关键结论：段内 if 是**免费**的，⛔ 不引入「跨段调度脚本」

**段脚本本身就是完整 Python 文件** ⇒ 它内部想怎么 if 就怎么 if（检测页面特征 → 选不同选择器 → 返回 rows/artifact），**不需要任何新机制**。

- 段内 if：**作用域受限**，出错只影响一段，可单测 ⇒ 推荐。
- 跨段调度脚本：需要跨段共享状态/中间结果，而段间契约只传 `row + html`（M 节）⇒ **传不了复杂状态**，硬做就要扩契约 ⇒ 复杂度净增。

⇒ **⛔ 不新增「调度脚本」类型**；需要分支就写在段脚本里（天然支持）。

### N5 两种形态应**并存**（⛔ 不强制拆）

| 形态 | `# role:` | 适用 |
|---|---|---|
| 段脚本 | `entry` / `pick` / `toc` / `content` | 结构通用、可复用给别的站 |
| 整站脚本 | `pipeline` | ① 站点结构独特（段复用不出去）② 段间耦合紧（要共享状态/中间结果）③ 一次写好长期低频改 |

⇒ flow 配置里可填「一个 `pipeline`」直接跑，也可填「N 个段」。**拆不拆由脚本作者（AI）判断**，⛔ 不由机制强制。

### N6 ⛔ 不引入 dispatch DSL

若将来想声明「按页面特征选段」（如 `dispatch: toc by has(".chapter-list")`）⇒ 那是**自定义小语言**：维护成本高、AI 易写错、文档要养。

⇒ 宁可让 AI **在段脚本里写 Python if**（免费、可读、可调试），⛔ 不造 DSL。

### N7 决策建议

1. **做**：A 试跑推荐（内置，期①）+ B flow 静态编排（期①）。
2. **天然支持**：段脚本内部分支（无需任何改动）。
3. **不做**：跨段调度脚本、dispatch DSL。
4. **允许**：`pipeline` 整站脚本与段脚本并存，flow 两种都能引用。

### N8 待拍板

1. 确认「⛔ 不引入调度脚本 / dispatch DSL，段内 if 免费」这条边界？—— **按推荐默认**（2026-10-20）：不引入，段内 if 免费。
2. ✅ `pipeline` 与段脚本并存、由 AI 自行判断拆不拆 —— **用户 2026-10-20 拍板：同意**（详见 N9 契约写法）。
3. A 试跑推荐作为唯一"自动判断"手段，判据（条数>0 且必填字段非空率最高）—— **按推荐默认**。

### N9 形态选择指引（🔴 待写进「规则格式契约」，给 AI 的判断标准）

| 选哪种 | 判定 |
|---|---|
| **段脚本**（默认） | 这段结构通用、能想到别的站也能用 ⇒ 拆出来复用 |
| **`pipeline` 整站脚本** | ① 站点结构独特（段复用不出去）② 段间要共享状态/中间结果 ③ 一次写好、低频改 |

- 权威来源是脚本头 `# role:`（⛔ 不从文件名猜）；无 `role` 的老脚本按 `pipeline`。
- 命名建议：`generic-novel-content.py`（通用段）/ `qidian.py`（整站）；**通用段加 `generic-` 前缀**便于一眼分辨可复用性。
- `flow` 配置两段都能引用：填一个 `pipeline` ⇒ 直接跑；填 N 个段 ⇒ 按 `entry→pick→toc→content→save` 串。
- **段内 if 允许且推荐**（页面特征检测 → 选不同选择器），⛔ 不为此新增机制。
