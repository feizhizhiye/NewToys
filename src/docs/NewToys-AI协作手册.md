③ 实施期每完成一条工作项 → 在《状态与路线图》三、翻 `✔ 已完成（待验收）`，并在 `src/docs/backlog/NT-xxx.md` 追加「执行记录」；功能级交付 git commit（<type>: <简述>）；纯修报错不回写台账。⛔ 不写 md 日志——版本记录一律走 git。
④ ⛔ 不逐次改文档：需求/规范/协作手册是指导性文件，只在其内容真的过时/与代码冲突时才改；各文档独立升版本（不齐步）。
⑤ AI 维护分工（v3.0）：
   - 需求：只有框架级/边界级变化才动；单页实现细节一律不改需求。
   - 工程规范：实现模式/踩坑/技术债变了才动；本任务学到的具体细节可补进 §2/§3。
   - 台账：每个功能完成必更新。
   - 协作手册：仅流程变化时动。
⑥ **阻塞上报（Escalation / Blocker）** —— 必须停下来问：要改框架层 / 要删用户已确认的实现 / 需求自相矛盾 / 文档与代码冲突且影响本次 / 缺关键标识符。
   其余一律按最合理假设推进，并在交付里标注假设；⛔ 不反复确认细节（省往返 token）。
⑦ **Spec-first（v3.18 术语更新，行为不变）**：用户提出新需求 → **立项**（整理写入《需求规格》，必要时同步规范）→ 建工作项（《状态与路线图》三、）+ 写任务卡（`src/docs/backlog/NT-xxx.md`）→ 过 **就绪闸门**（升 `✅ 就绪`）→ **才实施**（改代码）→ 回写台账 → 验收 → 归档（任务卡**全量保留** ⛔ 不删）。⛔ 不得先改代码、后补文档；⛔ 需求理解有歧义或要改需求文档，先跟用户确认。

## 术语对照（Glossary）🔴 **全局唯一定义处**

> v3.18 新立。项目早期的说法是边做边起的名（待办 / 待办细节 / 草稿闸门 / 折衷项 …），此处统一映射到**业界标准术语**，方便与外部工具 / 他人 / 其它 AI 对齐。
> 🔴 **行为一律不变，只换说法** —— 状态机、闸门、批量协议照旧。⛔ 其它文档 / 入口不另立术语。
> 左侧「本项目说法」在今后的文档与对话中逐步淘汰，统一用右侧标准名。

### 流程（需求 → 交付）

| 本项目说法 | **标准术语** | 含义 |
|---|---|---|
| 用户提需求 → AI 整理 → 生成待办 | **立项（Kickoff）** | 需求被确认、正式进入研发管道的那一刻 |
| 规划 / 执行双模式 | **规划期（Planning）/ 实施期（Implementation）** | 两段式：先只想清楚写文档，再集中写代码 |
| 规划模式 | **规划期** | 只产文档，⛔ 不碰 `src/` |
| 执行模式 | **实施期** | 显式触发才改代码 |
| 变更顺序 / 顺序铁律 | **Spec-first（先立规格后实现）** | 需求未立规格不动代码 |
| 停手 5 种 | **阻塞上报（Blocker / Escalation）** | 停下来问用户，⛔ 不擅自扩范围 |
| 草稿闸门 | **就绪闸门（DoR · Definition of Ready）** | 进入实施前必须满足的**准入**清单 |
| 验收标准 | **验收标准（Acceptance Criteria）** | 任务卡里那条可勾选的清单 |
| （缺对应说法） | **完成定义（DoD · Definition of Done）** | 交付前必须满足的**准出**清单 = 本文件 [6] 自检 |
| 静态自检 | **静态检查（Lint / Pre-commit Check）** | `skill/scripts/check*.ps1` |
| 需本地验证点 | **手工回归清单（Manual QA Checklist）** | 编译不了 → 交给用户实机过的那几条 |
| 批次 | **变更集（Change Set）** | 一次交付里的一批改动 |
| 验收 | **验收（Acceptance）** | 用户实机确认，通过后翻 Accepted |
