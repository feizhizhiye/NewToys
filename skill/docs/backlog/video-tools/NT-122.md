# NT-122 · 转码前收益判定（省体积闸门）
- 状态：✔ 已完成（2026-10-31 编译通过）
- 优先级：P1
- 关联需求：需求规格 §6.4.23
- 依赖：NT-104（目标体积模式）、ffprobe 探测链路（`VideoScanner`）
- 创建：2026-10-31 ｜ 更新：2026-10-31

## 背景 / 目标
用户现象：「有的 H.264 视频转成 H.265 后体积反而变大」。原因是源码率已压到 H.265 的视觉透明线以下，
再按 CRF 23 重编码只会把比特重新分配，加上音轨被强制重编到 192k，总体反而增大。

本卡做**转码前的静态判定**：用源属性（总码率 / 分辨率 / 帧率 / 编码族 / 音轨码率）算 bpp，
对照目标编码族的透明线，判断这次转码还能不能真的省体积；不值得就按策略跳过。

⚠️ 不预测体积点值（CRF 编码体积取决于画面复杂度，静态算不准），只判方向 + 给区间口径，
并保留 `Unknown` 档（信息不足时一律放行）。

## 验收标准
- [x] `TranscodeAdvisor`（纯函数，无 IO / 无 UI）给出 `Worth / Marginal / Skip / Unknown` 四档 + 预估省幅；
- [x] 判据 = `bpp = 视频码率 ÷ (宽 × 高 × 帧率)` 对比目标族透明线（x264 0.10 / x265 0.06 / AV1 0.05），速度档按 medium 折 1.25；
- [x] 音轨单独精算：目标音轨码率高于源时，算出 `+N MB` 并提示「音轨吃掉视频收益」；
- [x] 目标体积模式（`TargetSizeMb > 0`）不看内容复杂度，直接按体积比给结论（确定值）；
- [x] 只换容器（`copy`）判据独立：音轨原样 ⇒ 判「体积几乎不变」；
- [x] 建任务时（批量页 / 预览页 / 编辑互转）自动算好，详情卡「转码」节显示「收益预估：…」一行；
- [x] `ffprobe` 补抓音轨码率与音轨条数（原来 `-select_streams v:0` 导致音频流根本拿不到）；
- [x] 设置页「视频工具设置 → 性能」新增策略下拉（建议 / 严格 / 关闭）+ 省幅门槛（0~90%，默认 10%）；
- [x] 严格档：`▶▶ 批量运行` 时预估不值得的任务标 `已跳过`（不算失败、不跑 ffmpeg、`Message` 写原因）；
- [x] 底部摘要显示「已跳过 N（预估不值得转）」；
- [x] 缺帧率 / 分辨率时按 `Unknown` 放行（宁可多转一个，不误杀）；帧率缺失按 25fps 估、码率可由文件大小反算。

## 技术要点
- 判定入口 `TranscodeTask.RefreshAdvice(minSavingPercent)`；参数变化（CRF / 分辨率 / 预设 / 音轨 / 目标体积）自动重算，
  `_filling` 守卫阻止补值递归。
- `AdviceModes` 三档 + 门槛存 `config\video-tools.json`（`adviceMode` / `adviceMinSavingPercent`），
  `IVideoToolsSettingsService` 是唯一写入点。
- 新增状态 `VideoTaskStatus.Skipped`：**不进** `IsFinished` 的重跑语义例外 —— `▶▶` 仍可重跑失败 / 取消，
  只排除 `Done` 与 `Skipped`。
- `TranscodeAdvice` 记录随任务落库（JSON 序列化），重开软件后详情卡仍显示上次结论。
