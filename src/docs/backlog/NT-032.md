## 背景 / 目标
`ScanService` 的 `StorageIndex.BySizeMtime` 用字典索引器 `BySizeMtime[(size,mtime)] = l` 赋值，相同 `(size, mtime)` 的多条位置会**互相覆盖**；`IndexOne` 的匹配级 ② 把任意 `(size, mtime)` 命中当作"同一文件被移动" → `ApplyMove` 把那条已有位置改写到当前文件路径。

后果（实测可达）：用户用**保留时间戳**的工具（robocopy /COPY:DAT、部分镜像软件）复制出副本时，副本与原文件 `(size, mtime)` 相同 → 扫描把原文件的位置"移动"到副本路径，原文件真实路径在收尾被判 `missing`（下次扫描即"丢失"），索引错位。

## 验收标准
- [ ] 复制（保留 mtime）出的文件不再触发原文件位置的"移动"改写；原文件与副本各自正确建档。
- [ ] 相同 `(size, mtime)` 的多候选在内存索引中**不丢失**（多值存储）。
- [ ] 唯一候选时仍按"移动"处理（保持现有改名/移动识别能力）。

## 技术要点 / 约束
- 🔴 `BySizeMtime` 改为 `Dictionary<(long,string), List<FileLocation>>` 多值；`Add` 不再覆盖。
- 新增 `TryGetSingleBySizeMtime(size, mtime)`：**仅当唯一候选**时返回该位置；多候选 / 缺失返回 `null` → 匹配级 ② 回落到"新文件"（安全，杜绝错配）。
- ⛔ 不改 ③ quick_hash 与 ④ 新文件的既有逻辑；③ 是基于内容的、正确的，保持。
- ⛔ 不动框架层；仅改 `Module.MediaAssets/Services/ScanService.cs` 的 `StorageIndex` 与 `IndexOne`。
