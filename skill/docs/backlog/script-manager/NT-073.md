## 一、背景与目标

现状三个问题：

1. **`kind` 是摆设** —— 集合卡能改 kind 并落盘，但信息面板的集合下拉不过滤 kind，任何集合都能进去；刷新策略 / 视图字段只做「显示与否」，不做禁用。
2. **集合列表看不出谁在用** —— 信息面板当前集合（`lastCollectionId`）在集合页有「在用」，但脚本库 / 命令库页各自正在用的库没有任何标记（只能翻详情卡）。
3. **脚本库 / 命令库不是「索引」** —— 两个页面直接列全库条目，集合只当分组容器；用户无法按「不同文件夹的脚本索引」组织多套库。

目标：**集合 = 索引容器**（kind 决定归哪个页面），页面 = 该 kind 全部集合的可采集成员并集；
内置两库改名「默认脚本库」「默认命令库」，用户可再建多个库，每库可有自己的根目录。

## 三、契约与决策（验收基线）

### 三.1 术语与归属（🔴 消歧）

| 概念 | 定义 | 说明 |
|---|---|---|
| 库 | `kind ∈ {script, command}` 的集合 | 不是新实体，复用 `ScriptCollection` |
| 页面 | 脚本库页 / 命令库页 | **既是展示页也是收录页**：主视图 = 当前库（`库 ▾`，可切「全部库」）；导入 / 新建的条目**必须归属一个库** |
| 在用 | 页面当前选中的库 | 信息面板 = `lastCollectionId`；脚本库 / 命令库各一个（新增按 kind 分键） |
| 可采集 | `item.Collectable == true` | 脚本 = 扩展名合法且文件存在；命令 = 不在副作用黑名单且 `capture=true` |

### 三.2 决策（实施前不再改）

| # | 决策 |
|---|---|
| D1 | **库页 = 集合的展示 + 收录入口**（用户 2026-10-19 澄清）：页面通过 `kind` 对应的集合展示内容；`库 ▾` 选当前库，另有「全部库」看并集。⛔ 「条目不属于任何库」不是合法常态 —— 收录（导入 / 新建 / 扫描）必须先有目标库，孤儿只在删库瞬间出现，由 S5 收回默认库 |
| D2 | 主视图 = **当前库的可采集成员**；「全部库」= 该 kind 全部库的成员并集 ∩ role 匹配 ∩ `Collectable`。两种视图共用同一仓储方法 |
| D3 | 同一物理文件只对应**一条** item（按绝对路径去重）；多库共享同一条 → 删库不会删条目 |
| D4 | `ScriptCollection.RootPath`：空 = 用全局脚本目录（设置页那项降级为「默认根」）；相对路径 `Target` 相对**所属库**的 RootPath 解析 |
| D5 | 内置两库：`脚本库` → **`默认脚本库`**、`命令库` → **`默认命令库`**；`Builtin=true` ⇒ 不可删（改名、**改类别都可以**；改类别后下次启动由 `Normalize` 补回该 kind 的默认库） |
| D6 | 「在用」标记按 kind 分键：`lastCollectionIdByKind`（info / script / command）；老字段 `lastCollectionId` 作为 info 的兼容读入，迁移后写新结构 |
| D7 | 非 info 集合：刷新策略 / 刷新间隔 / 默认视图 / 视图数 **`EnabledWhen=IsInfoCollection` 禁用**（不是隐藏），数据保留 |
| D8 | 删库：删成员关系 + 删库定义；只属于该库的条目 → 收回**同 kind 的默认库**；⛔ 不删条目、⛔ 不删文件。默认库不可删 ⇒ 一定存在回收处 |
| D9 | 复制库：复制定义 + 视图 + 成员关系；`RootPath` 一并复制（用户可再改） |
| D10 | 🔴 **内置库不再全量同步**：`SyncBuiltinCollections` 改为「只接纳**不属于任何库**的条目」（新条目默认落地库），⛔ 不再把全部 script/command 角色硬塞进默认库 —— 否则多库时默认库会吞掉所有条目 |
| D11 | 导出两种：① **索引包** `.json`（库定义 + 成员相对路径 + `rootPath`，可读可手改）② **全量包** `.zip`（索引包 + 脚本文件本体）；命令库只支持 ① |
| D12 | 导入：索引包 → 新建库（名称冲突则加后缀）；全量包 → 解到所选目录并建库，`rootPath` = 该目录；文件冲突默认**跳过**并在结果里逐条列出（⛔ 不静默覆盖） |
| D13 | **集合页右栏候选池按集合 kind 过滤**（用户 2026-10-19）：选中 `script` 集合 ⇒ 候选 = 所有 `kind=script` 库的可采集成员（role∈{script,collector}）；`command` 集合 ⇒ 所有命令库成员（role=command）；`info` 集合 ⇒ 全部可采集条目（可混脚本 + 命令，这是设计本意）；`package` ⇒ `role=package`。另给「显示全部类型」开关（默认关）允许跨类勾选，⛔ 不替代「显示不可采集」 |
| D14 | **左栏每行显式标种类 + 在用**（用户 2026-10-19「更直观」）：第一行 = 名称 + 右侧 kind 徽标（`脚本` / `命令` / `信息` / `包`）；第二行 = 成员数 +「在用」；★ 置顶仍在行尾。徽标用主题语义键（`accent` / `secondary` / `hint`），⛔ 写死色值 |
| D15 | **库页删除条目 = 从当前库移出**（用户 2026-10-19 选 1）：多库时只解除当前库的成员关系，⛔ 不删条目本体、⛔ 不删文件；条目因此不再属于任何库时按 D8 收回默认库；要彻底删条目走集合页的条目删除 |

## 四、验收标准

1. 信息面板 `集合 ▾` 只出现 `kind=info` 的集合；没有时显示空态引导，⛔ 不出现脚本库集合。
2. 集合卡把 kind 切到 `info` / `script` / `command`：刷新策略、间隔、默认视图字段的**可用性**随之变化（非 info 灰显且不可编辑，值不丢）。
3. 脚本库页选中库 A 后，集合页左栏 A 显示「在用」；命令库页同理，两页标记互不覆盖（切页后各自保持）。
4. 脚本库页默认显示「当前库」的成员且全部 `Collectable=true`；切「全部库」后显示所有 `kind=script` 库的并集，每行「所属库」正确。
5. 命令库页同理（只列命令；⛔ 无根目录字段）。
6. 新建第二个脚本库并设不同根目录 → 两库脚本各自可看可切；同名文件在不同根目录是两条；在库页导入文件夹 ⇒ 文件成为当前库成员。
7. 删除库 B：B 的成员关系清除；只属于 B 的条目出现在默认脚本库；文件仍在磁盘；同时属于 A 的条目不受影响。
8. 内置「默认脚本库 / 默认命令库」：可改名、⛔ 不可删、⛔ kind 不可改；新建条目自动只落默认库，⛔ 不再被全量同步。
9. 导出索引包 → 在另一台/另一配置导入 ⇒ 得到同名库 + 成员清单；导出全量包 ⇒ 解包后脚本可运行；文件冲突默认跳过并列出。
10. 老 `script.json` 可无损打开（`lastCollectionId` 迁移 + `RootPath` 缺省为空）。
11. 集合页选中 `脚本库` 集合 ⇒ 右栏候选只出现该 kind 库的可采集脚本（命令不出现）；选中 `命令库` ⇒ 只出现命令；选中 `信息面板` ⇒ 脚本 + 命令都在；打开「显示全部类型」后跨类候选出现。
12. 集合左栏每行能直接看出种类（徽标）与在用状态；★ 置顶不丢。
13. 库页对条目执行「删除」⇒ 仅从当前库移出，其他库仍能看到该条目，文件不动。
14. `pwsh skill/scripts/accept.ps1` 全绿。

## 五、技术要点

- `ScriptStore.ScriptCollection`：`+ RootPath`；`ScriptStoreData`：`+ LastCollectionIdByKind`（`Dictionary<string,string>`），保留 `LastCollectionId` 供迁移。
- `ScriptStoreService.Normalize`：迁移老 `lastCollectionId` → `byKind["info"]`；`RootPath` 规范化（去尾部 `\`）。
- 新增仓储方法：`IReadOnlyList<ScriptItem> CollectableItemsOfKind(string kind)`（并集 + 去重 + 可采集过滤）与 `string ResolveAbsolutePath(ScriptItem)`（按所属库 RootPath）。
- `ScriptInfoViewModel`：集合下拉加 `kind == Info` 过滤；`lastCollectionId` 读写改走 `byKind["info"]`，首次为空时落第一个 info 集合。
- `ScriptLibraryViewModel` / `CommandLibraryViewModel`：`QuickActionListViewModel` 的数据源需支持「按 kind 并集」——优先在 `QuickActionService` 内按 `PageKind` 增设过滤，避免动基类契约；若必须动基类 ⇒ 属框架层相邻改动，实施前单独确认。
- `CollectionViewModel`：`IsInfoCollection` 同时驱动 `EnabledWhen`；`RefreshUsageState` 改为读 `byKind` 判断三类在用；排序里 info 沉底改为「kind==info 且在用」；`LoadMemberTable` 的候选源改为 `CandidateItemsFor(collection.Kind)`（+ `ShowAllKinds` 开关放开）；`CollectionRow` 加 `KindBadge` / `KindBadgeClass`（由 `Kind` 派生，`OnKindChanged` 一并通知）。
- 左栏 XAML：行模板第一行改成 `Grid ColumnDefinitions="Auto,*,Auto"` = 图标 / 名称 / kind 徽标；第二行 = 成员数 + `InUseMark`（NT-072 已有，复用）。`CollectionRow.SubText` 相应去掉 kind 前缀（避免与徽标重复）。
- `BuildinCollectorSeeder` / `ExampleSeeder`：默认脚本库根 = 全局脚本目录；示例脚本仍播进默认脚本库成员。
- `ScriptStoreService.SyncBuiltinCollections`：改为「`item.Collections` 为空 ⇒ 按 role 收进对应默认库」，⛔ 不再对已归属其他库的条目增删成员（D10）。
- 导入导出：新增 `Services/ScriptLibraryPackageService`（模块内）—— `ExportIndex`（json）/ `ExportBundle`（zip：`library.json` + `files/…`）/ `Import`（解包 → 建库 → 建/复用条目，按绝对路径去重）；⛔ 不放在 Shared/Core（只此模块用）。
- 库页工具条（`IToolbarSource`）：`库 ▾`（Combo）+ `📂 导入文件` + `📂 导入文件夹`（SplitButton）+ `🔍 扫描目录` + `📥 导入库` + `📤 导出库` + 搜索；现有「仅可采集」筛选可保留。
- ⚠️ 命令库没有「根目录」概念（命令是命令行字符串）⇒ `RootPath` 只对 `kind=script` 生效；命令库集合保留字段但 UI 隐藏，导入导出只支持索引包。

## 六、依赖 / 风险 / 待拍板

- 依赖 NT-068（四层模型）、NT-072（在用标记）、NT-072 的 `OnAttachedToVisualTree` 刷新钩子。
- **风险 1**：库页数据源改「按库/并集」会动 `QuickActionListViewModel`（被脚本收集 / 命令收集页共用）⇒ 优先只在 `QuickActionService` 适配层加 `PageKind` 过滤，⛔ 不改基类行为。
- **风险 2**：`script.json` 结构变更 ⇒ 必须先做迁移 + 备份（`script.json.bak-<时间>`）；迁移失败不覆盖原文件。
- **风险 3**：`missing` 判定从「全局脚本目录」改为「所属库 Roots」⇒ 老数据若根目录不同会集体变 missing，需要「迁移时把老库 RootPath 置空（= 全局目录）」保证不变。
- **风险 4**：全量包解压必须防路径穿越（`..` / 绝对路径）—— 与 NT-067 的 zip 导入同一坑，先判路径再跳过白名单。
- **已定（原待拍板 1）**：库页 `库 ▾` 需要，默认 = 上次用的库，另有「全部库」。
- **已定（原待拍板 2）**：导出两种包（索引包 / 全量包），命令库只有索引包。

### 偏差（实现与卡不一致处，均按风险更低方案落定）

3. **「全部库」视图下扫描 / 导入**用全局脚本目录（不弹选库），新建条目仍落默认库；选具体库时按该库根。
4. **`missing` 判定未按库根改造**：`ScriptScanner` 仍按相对路径去重，跨库同名文件可能被判「已入库」。已记录，后续需要再立卡。
5. **全量包导出**只复制 `rootPath` 下真实存在的文件；`rootPath` 为空时只导索引。
