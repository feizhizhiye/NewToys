## 一、背景与问题

需求 §2.3.2 把 `web-scrape` 的终态定为「脚本库的 `category=rule` 筛选态」—— 即左树不再有独立的「抓取规则」页，规则就是脚本库里的 `Category=rule` 条目。

**NT-089 实施时实测：这个改法不成立。**

`Views/RuleCatalogView.axaml` 绑的不是通用列表命令，而是 `RuleCatalogViewModel` 的**规则页专属**命令：

| View 绑定 | 命令 | 丢了会怎样 |
|---|---|---|
| `NewRuleSetCommand` | `NewRuleSet()` | ⛔ 不能新建规则集（含「从预设创建」入口，NT-086 批 E） |
| 站点网址框 + `ProbeSiteCommand` | `ProbeSiteAsync()` | ⛔ 站点探测失效（NT-086 批 E，7 个预设命中推荐） |
| `ToggleEnabledCommand` | `ToggleEnabled()` | ⛔ 启停失效 |
| `EditRuleSetCommand` / 双击行 | `EditRuleSet()` | ⛔ 进不了调试集合 |
| `OpenFileCommand` / `OpenFolderCommand` | `OpenFile()` / `OpenFolder()` | ⛔ 打不开规则文件 / 目录 |
| `OpenRunsFolderCommand` | `OpenRunsFolder()` | ⛔ 打不开运行记录目录（NT-086 批 G） |
| `ExportCsvCommand` / `ExportJsonCommand` | `ExportCsvAsync()` / `ExportJsonAsync()` | ⛔ 运行记录导出失效 |
| `DeleteCommand` | `DeleteAsync()` | ⛔ 删不了规则集 |

卡 §二.S2.3 写的是「只把 `x:DataType` / 绑定目标改指 `RuleLibraryViewModel`」⇒ 照做 = 上面 10 个命令全删 + UI 绑空。属铁律「⛔ 不删用户已确认的实现」⇒ **上报拍板**。

## 二、方案（三选一）

### 方案 A · 不合并（089 就此结在 S1，⛔ 不再动）

保留 `RuleCatalogViewModel` + 独立「抓取规则」页。

- ✅ 零风险、零回归，已实施代码不动。
- ⚠️ 左树「脚本中心」下会有两个"规则"入口（脚本库 + 抓取规则），概念重复 —— 正是 §2.3 想消除的东西。
- ⚠️ 需求 §2.3.2 表里那行要改回去（写「保留独立目录页」）。

### 方案 B · 合并退化（保留全部功能）

1. 新增 `ViewModels/RuleLibraryViewModel.cs`：`sealed partial class RuleLibraryViewModel : QuickActionListViewModel`，构造后预置 `SelectedCategory = "rule"`、锁定分类筛选（列表只显示 rule 条目）。
2. 🔴 **规则页专属工具条整体搬进 `RuleLibraryViewModel`**（`NewRuleSet` / `ProbeSite` / `ToggleEnabled` / `EditRuleSet` / `OpenFile` / `OpenFolder` / `OpenRunsFolder` / `ExportCsv` / `ExportJson` / `Delete`），走基类已有的 `ToolbarExtras` / `ToolbarTailExtras` 插槽拼装 ⇒ **功能一个不丢**。
3. `RuleCatalogView` 保留作 `web-scrape` 的 View，只换绑定目标（⛔ 不删 View：不动壳、保留列宽/详情栏偏好）。
4. 删 `ViewModels/RuleCatalogViewModel.cs`。
5. 规则条目的来源：⛔ 不改存储格式 —— 新增「扫描 `<DataDir>\script\rules\*.py`」的入口，产出 `QuickAction`（`Category=rule`）后合并进脚本库条目集合（与 `ScriptScanner` 扫 `<DataDir>\scripts` 并列）。

- ✅ 达成 §2.3.2 终态，且功能零回退。
- ⚠️ 成本比卡估的高：`RuleCatalogViewModel` 约 1000 行的工具条 / 探测 / 导出逻辑要平移，且要与基类的 `ToolbarExtras` 机制对齐（含 `IToolbarOwner` 的 `CommandPath` 解析）。

### 方案 C · 撤出菜单、保留页面（折中）

`RuleCatalogView` / `RuleCatalogViewModel` 注册保留（供 `NavigateTo`），但**从左树撤下** ⇒ 用户只从脚本库进入规则页。

- ✅ 左树不再重复，改动极小（一行注册删掉）。
- ⚠️ 页面入口变隐蔽（与 NT-084 末期「`web-rule-editor` 撤出菜单」同款问题，当时用户要求挂回菜单）⇒ 与既有定调冲突。

## 四、技术要点

- 🔴 **基类已有插槽**：`QuickActionListViewModel` 有 `ToolbarExtras` / `ToolbarTailExtras`（拼装工具条），`IToolbarOwner` 决定 `CommandPath` 相对谁解析 ⇒ 方案 B 的规则工具条靠它挂上去，⛔ 不要另造一套工具条机制。
- 🔴 **条目来源合并**：`QuickActionService` 落 `config\script\script.json` / `data\script\script.db`；规则扫描产出 `QuickAction`（`Category=rule`）⇒ ⛔ 不改存储格式、⛔ 不上提 Core。
- 🔴 **规则参数化执行归 NT-092**（`base_url` / 变量占位符），本卡不做。
- 规则文件是用户自建资产 ⇒ 目录常量若再动，必须配一次性搬迁（NT-089 的 `RuleFileService.MigrateLegacyRules` 即范本）。
