## 一、定位

**NewToys 是作者个人自制的工具集——「带 GUI 的脚本管理器」。** 非商业、非通用产品，「自用顺手」第一。

每个页面 ≈ 一条或几条命令行 + 一份 `config/` 配置的封装。

## 二、边界

**判据**：「如果我只写个脚本会怎么写？现在少让用户做哪一步？」——这就是功能边界。

- **做**：把作者日常高频的终端/系统能力，包成可点、可配、可备份的界面。
- **不做**：脚本里不会有的东西——社交、推荐、引导、埋点、账号、云同步、**在线插件市场/商店**。
- **本地模块热加载**（丢 DLL 进 `modules/`、点按钮装载）**要做**——它不联网、不下载、不建生态，等于「加一个本地脚本」，不是"插件市场"。

## 三、技术框架（硬约束）

> 本节锁「软件框架长成什么样」。具体像素/类名/API 签名/踩坑见规范。

### 3.1 分层与依赖

```
Shared（契约/模型，不引 Avalonia）
  ▲
Core（服务实现，不引 Avalonia）
  ▲
Shell（宿主，引 Avalonia，AssemblyName=NewToys → NewToys.exe）
  ▲
Module.*（功能模块，只引 Shared+Core）
```

- **单向依赖**，禁止反向。
- **禁止模块引用 Shell**（循环依赖）；**禁止模块之间互相引用**；跨模块协作走 `Shared` 契约。
- **Shared/Core 禁止引用 Avalonia**（系统明暗/平台能力由 Shell 探测后注入）。
- **公共基类/契约放 Shared**；被 ≥2 模块用或属应用级能力才上提，判断不清默认放模块内部。

### 3.4 模块化与热加载

- 模块编译为独立 DLL（命名 `Module.<模块名>.dll`），实现 `IModule { RegisterServices, Initialize }`。
- **菜单只能在 `Initialize` 注册**；`RegisterServices` 禁注册。
- **启动双轨**：Debug 用 `#if DEBUG` 显式类型清单；Release 扫 `<程序目录>\Modules\` 目录，跳过已加载同名。
- **运行期热加载**：丢 DLL 进 `Modules\` → 点 UI 刷新 → 即时装配，不重启。
  - 只读本地 `Modules\`，**不联网不下载**；`Path.GetFullPath` 校验路径在 `Modules\` 内。
  - 每个 DLL 用独立 `AssemblyLoadContext`（`isCollectible:true`）；`NewToys.Shared/Core` 由默认 ALC 共享。
  - 逐个 `try-catch` 隔离：单 DLL 失败不影响宿主与其他模块。
  - 本版只做「新增」，同名不替换不卸载（详见规范折衷台账 B10）。

### 3.5 配置与数据

- **多配置（v3.5）**：应用根下按「配置」分目录 —— `<应用根>\profiles\<配置名>\{config,data,logs}`；**当前配置**记在 `<应用根>\active-profile.txt`（必须放在 `profiles\` **之外**，否则切换时把自己也换掉了）。
- **所有设置落 `<配置根>\config\*.json`**（才能被数据管理页备份/导入）。
- **用户功能数据**同样落 `config\`、一样进备份。
- **本地数据库**落 `<配置根>\data\newtoys.db`（可随时重建的缓存，**不进备份**）。
- **日志**落 `<配置根>\logs\`。
- **应用根**：`%LocalAppData%\NewToys`，环境变量 **`NEWTOYS_HOME`** 整根切换（test vs prod）；「配置」是在应用根**之内**再分一层。
- **数据迁移（v3.5）**：首次运行新版时，若 `<应用根>\config` 存在而 `<应用根>\profiles` 不存在 → 把现有 `config/data/logs` **整体移动**到 `profiles\default\`，并写 `active-profile.txt = default`；移动失败则**保持旧结构运行**，并在「设置 → 配置」提示。
- **切换配置 = 重启应用**（配置在启动时被大量单例服务读取；热切换改动面大、且极易残留半新半旧的状态）。
- **模块只读设置**，唯一写入点在该设置的设置页；功能入口页**只读**（⛔ 不许回写→双真相源）。
- **改系统级配置的页面必须二次确认**（如软件源增删 → 改系统 winget）。

### 3.6 默认数据（不许硬编码）

- **内容清单不写死在 C# 里**。
- 默认内容随程序发布在 `<程序目录>\defaults\*`，**首次运行**复制/播种成 `config\` 或用户目录下的用户文件。
- 此后一切以用户那份为准（用户删掉的条目不会被"复活"）。

### 3.7 跨平台预留

- 主平台 **Windows 10 LTSC**；迁移方向 **Debian 13**。
- 平台相关能力（winget / `ms-settings:` / ffmpeg）集中封装，便于整体替换。
- 路径一律 `Path.Combine`；外部相对路径 `Path.GetFullPath` 后校验落在目标目录内。

### 4.5 右侧详情面板（340px，可开合）

> ⏸ **本轮（v3.2）**：Shell 侧容器与 `IDetailPanelProvider` 契约**已实装**；**页面迁移（右列上提）暂缓**，各页仍用页内右列。

- **契约**（`Shared/Services/IDetailPanelProvider.cs`，页面 VM 可选实现）：

```csharp
public interface IDetailPanelProvider
{
    bool HasDetailPanel { get; }          // 该页是否有详情
    bool IsDetailOpen   { get; }          // 当前是否展开
    object? DetailContent { get; }        // 详情内容（绑定 ContentControl）
    event EventHandler? DetailChanged;    // 通知 Shell 刷新
    void ToggleDetail();                  // 表头 ▤ 按钮调这个
    void OpenDetail();                    // 右键「显示详情栏」调这个
}
```

- Shell 在标签切换时检查当前 VM：实现则显示右侧面板 + 订阅 `DetailChanged`；未实现则隐藏该列。
- 列表页的表头 `▤` 按钮 / 右键首项**改为调契约方法**（`ToggleDetail()` / `OpenDetail()`），由 Shell 响应。
- 面板宽度 340px；**是否展开**落 `config/columnlayout.json`（沿用 `FlagDetailPanel`，**按页面 Key 分别记忆**）。
- 面板隐藏时该列宽度为 0，内容区自动铺满。

## 五、导航模型（硬约束）

> v3.0 由「菜单驱动」改为「标签页驱动」。

### 5.1 核心概念

- 一个**标签页**（Tab）= 一个打开的功能页面 = 一个缓存的 View 实例 + 一份 VM + 一个历史栈。
- 打开页面的**唯一入口** = 标签页；菜单点击、搜索框回车、标题栏 ⚙、标签栏 `+` 都是「打开/激活某个 Key 的标签页」。
- 视图解析（`ResolveView`）逻辑保留，改为「为新标签页解析一次 View 并缓存」。

### 5.2 标签页模型（`Shell/ViewModels/TabItemViewModel.cs`）

```csharp
public partial class TabItemViewModel : ObservableObject
{
    public string Key { get; }            // 菜单 key，如 "pc-package"
    public string Title { get; }
    public string IconKey { get; }         // 图标资源键，如 "IconPackage"
    public object Content { get; }          // 缓存的 View 实例
    public object ViewModel { get; }        // 对应 VM（用于契约检测）
    public bool CanClose { get; }           // 首页 = false

    internal Stack<object> BackStack { get; }
    internal Stack<object> ForwardStack { get; }
    public bool CanGoBack { get; }
    public bool CanGoForward { get; }
}
```

`ShellViewModel` 新增：

```csharp
public ObservableCollection<TabItemViewModel> Tabs { get; }
public TabItemViewModel? ActiveTab { get; }

[RelayCommand] void OpenTab(string key);         // 打开/激活
[RelayCommand] void CloseTab(TabItemViewModel t);
[RelayCommand] void GoBack();
[RelayCommand] void GoForward();
[RelayCommand] void Refresh();
[RelayCommand] void ToggleTree();
[RelayCommand] void ToggleDetail();
```

### 5.3 历史栈

- **每个标签页独立维护**。栈元素是「页面内的导航状态快照」。
- **什么进历史栈**：
  - 可以进：目录切换（`video-list` 进入不同文件夹）；搜索执行（软件包页执行一次搜索）；从列表进入子详情（将来做「包详情页」时）。
  - 不进：列表内选中不同条目（选中态，非导航）；筛选/排序变化（视图状态，非导航）。
- **契约**（`Shared/Services/IHistoryProvider.cs`，页面 VM 可选实现）：

```csharp
public interface IHistoryProvider
{
    object? CaptureState();                          // 当前快照（null = 不记录）
    void RestoreState(object state);                 // 恢复
    event EventHandler? StatePushed;                 // 通知 Shell push
}
```

- 页面通过 `StatePushed` 通知 Shell push 当前 `CaptureState()`。
- 前进/后退时 Shell 调 `RestoreState`。
- **未实现 `IHistoryProvider` 的页面**：前进/后退按钮禁用（灰显）。

> ⚠️ **现状如实**：目前只有 `video-list` 有明显页内导航语义，其他页面基本无页内导航 → 前进/后退在多数标签页里会是灰的。这是如实状态，不是设计缺陷——按钮为将来页面级导航预留。
>
> **本轮（v3.1）**：`IHistoryProvider` 只**定义契约、无页面实现** → 前进 / 后退按钮**一律灰显**；`video-list` 的页内导航（目录切换）留到下一版。

### 5.4 启动时序调整

`ShellViewModel` 构造函数末尾：

- 原 `GoHomeCommand.Execute(null)` → **`OpenTab("home")`**（首页作为首个固定标签页）。

其余启动时序（DI → 模块加载 → 主题 → Show）不变。

### 5.5 防闪退铁律

1. `OpenTab` 找不到 key 不得抛异常 → 忽略并记日志。
2. `ActiveTab.Content` 为 null 时内容区显示空态，不崩。
3. 关闭最后一个标签页 → 自动打开首页（保证始终有激活标签）。
4. 关闭首页标签 → 拒绝（`CanClose=false`）。
5. 每个标签页的 View+VM 缓存；关闭时销毁（`IDisposable` 若实现则调用）。

#### 6.4.2 评估 A：同源多段剪辑（结论：**可行，分两步**）

> 需求原话："是否可以实现同一视频的多段剪辑 —— 可能会有多段剪辑命令。"

- **可行**。两种落法：
  - **方案 A（推荐，一期）**：**"多段 = 多条命令/多个任务"** —— 命令生成页可选"添加片段"，每段产出一条 `CutTask` 入队；批量页本来就是逐条跑的队列，**天然支持**（几乎不用改 `VideoTaskStore` 结构，只在 UI 上把"一个任务"扩成"一组片段"）。
  - **方案 B（二期）**：**"多段合成一个文件"** —— 单条 ffmpeg 命令用 `-filter_complex` 的 `trim` + `concat`（需重编码），或"分段 `-c copy` 各切一个文件 + concat demuxer 合并"（需中间文件）。成本与坑都更高。
- **建议**：一期只做**方案 A**（多段 = 多条命令），把"合成一个文件"留二期；`CutTask` 一期可**不改结构**，二期再加 `Segments` 列表。

#### 6.4.3 评估 B：命令生成函数 / 类 Excel 自动填充（结论：**可行，一期先做"单任务吸附"**）

> 需求原话："给这些命令增加生成函数，比如分辨率 2100×1500 自动调整到 1920×1080；就像 Excel 一样可以自动填充表格生成命令。"

- **可行且成本低**。本质是**一组纯函数**（放在 `Services/`，不碰 UI、不动模型），例如：
  - `SnapResolution(w, h)` —— 分辨率吸附。两种规则，**默认取"保比例、限长边"（不畸变）**；另提供"吸附标准档"（2160/1440/1080/720/480/360）：2100×1500 **两轴都超过 1920×1080** → 吸附到 **1920×1080**。
  - `SuggestBitRate(w, h, fps, quality)` —— 按分辨率 × 帧率 × 质量系数给目标码率建议。
  - `PickEncoder(cpuOrGpu, codec)` —— CPU/GPU 编码器映射（`libx264`↔`h264_nvenc` …）。
- **"类 Excel 自动填充"** = 把同一套规则**按行套用**：一张参数表（行 = 源文件、列 = 分辨率 / 编码器 / 码率 / 输出格式），填好首行 → 向下**批量生成每行命令**。
  - **一期**：先在**命令生成页**落"下拉 + 吸附/建议"（单任务的智能默认值）。
  - **二期**：再把"表格式批量填充"做进**批量处理页**（需先给批量页引入表格式参数编辑；属新增交互，成本中等）。

**统一队列的实现约定（v3.8 起沿用）**：
- 两类任务的**公共基类** `VideoTaskBase` 已含 `Status/Progress/Message/Name/StatusDisplay/OutputSize` → 批量列表直接用 `ObservableCollection<VideoTaskBase>` 合并 `CutTasks` + `TranscodeTasks`（**不改 `VideoTaskStore` 的存储结构**）。
- 运行按类型分派：`CutTask → FfmpegService.BuildCutArgs`，`TranscodeTask → FfmpegService.BuildTranscodeArgs`，统一走 `FfmpegService.RunAsync`。

## 七、设计原则（六条）

1. **模块化** — 按模块拆分，可独立开发/启停。
2. **插件化** — 模块编译为独立 DLL，运行时装配，加模块不改宿主。
3. **轻量务实** — 工具类应用，重效率稳定，UI 不炫技。
4. **自控** — 不引入任何第三方 UI 库/图标包，全局控件自己写。
5. **命令行封装** — 功能以「包既有命令行/系统能力」为主，不超命令行上限；配置一律落文件、可备份。
6. **可热加载** — DLL 放入程序目录 `modules/`（= `<程序目录>\Modules\`，单一目录），运行中点「刷新/加载」即时装配新模块，不必重启；加载源仅限本地文件夹。

## 十、文档体系

| 文档 | 回答 | 更新时机 |
|---|---|---|
| **本文件**（需求） | 做什么/为什么 + 技术框架 + UI 框架 + 导航模型 + 功能域 | 定位/边界/框架/职责变化时 |
| **开发规范** | 怎么具体做（编码模式 + 实现细节 + 折衷项 + 高频错误） | 具体实现方式变化时 |
| **项目现状与进度** | 做到哪了/还差什么 | 每完成一个功能/一次交付更新一次 |
| **AI协作提示词** | 本次会话怎么开工 | 协作流程变化时 |

- **单一权威**：同一条规则只在权威文档定义一次，其余引用不复制。
- **代码 > 文档**：冲突以 `src/` 源码为准并回写文档。
- **AI 介入前完善需求；介入后只按需求实现，边做边补规范/提示词，台账只记「做到哪了」。**
- **变更顺序（v3.3 明确）**：用户提出新需求 → **先整理写入本《开发需求》（必要时同步规范）** → **再改代码** → 最后更新台账。⛔ 不得先改代码、后补文档。
