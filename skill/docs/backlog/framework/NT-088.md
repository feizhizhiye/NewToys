## 一、背景与目标

2026-10-22「模块重划分 v1.1」（需求 §2.3）新建 **`system` 系统工具**模块，承接命令库 `script-commands` 与收藏夹 `script-favorites` —— 这两页都要**执行条目**。

而 `ScriptRunner` / `InterpreterResolver` 当前住在 `Module.ScriptManager`，**模块禁互引**（§3.1）⇒ system 拿不到。三条路：

| 方案 | 判断 |
|---|---|
| ① 上提 Core（`ScriptRunner` + `InterpreterResolver`） | ✅ **本卡采纳**：一份实现、一份语义 |
| ② 每个模块各写一份 Runner | ⛔ 双份维护（进程 / 编码 / 超时 / 杀进程树 / 取消），必然漂移 |
| ③ 允许模块互引 | ⛔ 违反 §3.1 分层铁律 |

🔴 **本卡对用户价值 = 零可见变化**（纯重构）；它的全部意义是给 §2.3 的后续分期铺路。

## 四、技术要点 / 约束

- 迁移面很小：`ScriptRunner` 现只依赖 `IAppConfigService`（Core）+ `IProcessRunner`（Core 已有）+ `InterpreterResolver`（同批上提）⇒ 主要是**改命名空间与 using**。
- **`IProcessRunner` / `ProcessRunner` 已在 Core**（NT-081 步骤 3 下沉）⇒ 本卡是同一方向的延续，二是为了把「脚本语义层」也归位。
- 改动落 Core ⇒ **整体重编**（按「一批一次 build」，建议本卡单独一批，便于定位）。
- 引用点清单（实施时先 grep 全仓确认，⛔ 不靠记忆）：`ScriptLibraryViewModel` / `CommandLibraryViewModel` / `FavoritesViewModel` / `CollectorService` / `EnvScriptsSeeder` / `ScriptInfoViewModel` / `PackageViewModel`（如有）/ `ScriptManagerModule.cs`。
- 行尾：工作区 CRLF（`core.autocrlf=true`）；脚本批处理用 `splitlines(keepends=True)` 原样写回。
- ⛔ 本卡**不做** `node(.js)` 解释器扩展（属 NT-092）、⛔ 不做命令链（NT-092）。
