## 背景 / 目标

用户 2026-11-04 反馈「每次启动 2-3s」，怀疑「每次读配置 json，能否硬编码预设一份」。
四轮摸底结论：**配置 json 不是瓶颈（<30ms）；用户日常双击的是 Debug 版，其必载模块清单早已硬编码（模块扫描 11~14ms）**。
现有打点从 `App.OnFrameworkInitializationCompleted()` 第一行起，`Main → CLR → UsePlatformDetect → WithInterFont → App.Initialize(App.axaml)` 全段未计时；
`framework.md §3.3` 已判「新编译产物第一次启动必然慢（冷读 + 杀毒实时扫描 + JIT）」，Debug 热启动基线 787~826ms。
用户体感 2-3s 与热启动基线的差额 ≈ **1.2~2.2s 冷启动环境开销**，落在未计时区。

本卡目标：**只补诊断，不提速** —— 把打点起点前移到 `Program.Main`，并在日志里标出产物配置 / exe / 冷或热，
一次性终结「日志混读 → 反复猜瓶颈」的循环。完整现状、实测与结案判断见 **`framework.md §3.5`**。

> ⚠️ **同日早些时候已做过完整实测闭环（临时打点 + 多次 build + R2R 试点，代码已还原）**：`LoadFrom` 1189ms 占 97%、热启动仅 2ms；并行加载无效（1203 vs 1222ms）；R2R 负优化已否决。详见 `framework.md §3.5` 头部与 §3.5.3。
> ⇒ 本卡 **⛔ 不重复**「模块扫描内部分项打点 / 并行加载 / R2R」，只补 `Main → OFIC` 这段从未计时的链路。用户 2026-11-04 确认「结案吧」后本卡 **✅ 已结案**，不再执行（结案以 `framework.md §3.5` 为准）。

## 技术要点 / 约束

- 🔴 **框架层**（`Shell/Program.cs` + `Shell/App.axaml.cs` / `App.Profile.cs`）：按约定**须用户确认后才可动手**；本轮只出方案，未改 `src/`。
- 打点起点 = `Program.Main` 第一行（静态 `Stopwatch`）；`App.Initialize` override 前后各一 Mark；`BuildAvaloniaApp()` 的 `UsePlatformDetect` / `WithInterFont` 分段包一层（不改链式调用语义）。
- 日志沿用 `App.Profile.cs` 的 `WriteStartupLog`（追加当天 `logs\startup-yyyyMMdd.log`、写盘失败静默），⛔ 不新引依赖、不新建日志文件、不加 UI。
- ⚠️ Debug 与 Release **共用** `%LOCALAPPDATA%\NewToys\profiles\<配置>\logs\`，不标产物就会继续混读（本轮四轮误判的根因）。
- ⚠️ `ConfigStoreService` 构造只算路径不碰磁盘（`Core/Services/ConfigStoreService.cs:55-63`），配置整理在首帧后 `InitializeDeferred`，⛔ 别把任何配置读取搬回热路径。
- 一次 build 完成；⛔ 不为打点单独再开卡；⛔ 不用单次启动日志下结论（§3.3 判据：连跑两次取第二次）。
- ⛔ 不重做已否决方向：并行加载模块 DLL / R2R 发布 / 模块扫描内部分项打点（历史实测 0 收益或负优化，见 §3.5.3）。
