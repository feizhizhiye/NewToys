## 四、使用层：操作逻辑 / 功能 / 使用方法的落点

用户口述的内容分五类，**各有唯一落点**，⛔ 不要一律塞进需求规格（需求规格只收"要做什么、验收标准"）。

| 用户说的 | 性质 | 落到哪 | 写法 |
|---|---|---|---|
| 「我要能 XXX」 | 新功能 | `NewToys-需求规格.md` 相关章节 + 任务卡 | 走立项 / 就绪闸门 |
| 「这页应该 XXX」 | 交互行为 | `modules/<模块>.md` §2.5 加一行 | 操作 → 触发 → 结果/状态变化 → 约束 |
| 「我一般这么用」 | 使用场景 | 说明书 §五 加一行 | 场景 → 操作路径 |
| 「这功能干什么的」 | 功能说明 | 说明书 §四 表加一行 | 页面 → 用途 → 要点 |
| 「这里坑，别 XXX」 | 踩坑 | `modules/<模块>.md` §5 | 症状 → 原因 → ⛔ 别做什么 |

**三条纪律**

1. **当场落，不等立项**：用法 / 操作逻辑是**知识**不是需求 —— 用户说完就地写进文档，跨会话不丢；⛔ 不许"先记在对话里，等有卡再说"。
2. **两份话、两个读者**：说明书 = 用户语言（点哪里、会发生什么、为什么这么排）；§2.5 = 契约语言（命令名、状态条件、写入时机）。同一行为两处都有 ⇒ **以 §2.5 为准**，说明书只写"用户能感知的部分"。
3. **改行为必须双写**：动了用户可见的交互 ⇒ 同一次改动里改 §2.5 + 说明书对应行；只改一处 = 交付未完成（与"回写台账"并列的第二条回写义务）。

## 五、任务卡目录规则

- 一个模块一个目录：`backlog/script-manager/` · `media-assets/` · `video-tools/` · `web-tools/` · `system-tools/` · `backup/`；跨模块放 `backlog/framework/`（应用级设置 / 首页的卡也归 framework，`settings-app/` 已于 2026-10-18 删除）。
- **每目录最多 5 张卡**；超了删**最旧且已验收**的那张；`📝草稿 / ✅就绪 / 🔄执行中 / ✔已完成（待验收）`不参与淘汰。
- **验收即蒸馏**：卡验收后把结论 / 偏差 / 坑写进 `modules/<模块>.md`，卡才可被淘汰。
- 格式与状态机见 `backlog/README.md`；流程与术语见 `NewToys-AI协作手册.md`。
